# AI 周报 · 技术方案

**版本** v1.7 ｜ **状态** M0–M8 均已完成：Electron 外壳 + Windows 安装包；按周归档与总览日历 + 总览页「上次记录」；复盘流改版（v0.9.0）—— 用户交整周原文，AI 一次调用给出五段复盘

> 配套文档：`产品设计文档.md` 讲**做什么、为什么做**。本文只讲**怎么做、为什么这么做**，
> 以及当时放弃了什么。

---

## 一、约束条件

先看实际环境，不猜：

| 约束 | 实测值 |
|---|---|
| Node | v24.9.0 |
| npm | 10.9.2 |
| Rust / cargo | **不存在** |
| 使用场景 | 个人自用、单机、一周用一次 |
| 目标平台 | 先桌面 |

三条硬约束决定了后面几乎所有的选择：

1. **没有 Rust 工具链** → Tauri 出局。省下的体积只在分发给他人时才值钱，而配置成本现在就付。
2. **个人自用、低频** → 不要账号、不要云同步、不要服务端。谁都不用在运维上花时间。
3. **产品成败在于「AI 理得对不对」**（见产品文档第十一节）→ 技术方案的首要任务是让这一步能最快迭代，而不是让架构好看。

## 二、选型总表

| 层 | 选型 | 为什么 | 放弃了什么 |
|---|---|---|---|
| 外壳 | Electron | 本机已有 Node 24，零额外环境；主进程可以写得很薄 | Tauri（缺 Rust 工具链） |
| 前端 | React 18 + TypeScript 5.6 + Vite 5 | 生态成熟、上手快、构建快 | Vue / Svelte（团队熟悉度没有优势） |
| 状态管理 | **不用库**，`useState` + `useRef` | 只有三个页面，一个 `App.tsx` 就管得过来 | Redux / Zustand |
| 网络层 | `ChatTransport` 接口 + 双实现 | 业务逻辑不直接碰网络，换外壳时上层不动 | 在组件里直接 `fetch` |
| AI 协议 | OpenAI 兼容 `/chat/completions`，SSE 流式 | 兼容 DeepSeek 等，换模型不用改代码 | 各家的原生 SDK |
| 结果校验 | 手写容错解析 + 代码层兜底 | 模型偶发不合法是常态，要的是「不崩」而不是「严格」 | zod（不是不行，是当前规模不值得） |
| 存储 | M2/M3: `localStorage`；M4: 主进程 JSON（配置 / 周归档两个文件） | 个人工具，本地优先 | 数据库、云同步 |
| 测试 | Vitest | 与 Vite 同源，零配置 | Jest |
| 打包 | electron-builder（M4） | Windows exe 这条路上坑最少 | electron-forge |

**没有引入的依赖**：UI 组件库、CSS 框架、状态管理、请求库、校验库。全部用原生 + 手写，
换来的是 `node_modules` 只有 101 个包、构建产物 184 KB。

## 三、分层与依赖方向

```

├── electron/       Electron 外壳。只开窗口与接线，一行业务逻辑都不放
│   ├── main.ts          主进程：开窗口、接 IPC、把文件读写接上
│   ├── preload.ts       预加载：渲染进程与主进程之间唯一的门
│   └── smoke.ts         启动冒烟检查（打包后「白屏了吗」只有真启动才知道）
├── src/
│   ├── core/          纯逻辑。不认环境、不碰网络、不碰界面
│   │   ├── types.ts           应用配置的形状与默认值
│   │   ├── aiClient.ts        AI 能力接口：一次调用换回一份复盘
│   │   ├── mockAi.ts          假 AI：按关键词的规则分析器
│   │   ├── openAiClient.ts    真实模型实现
│   │   ├── createAiClient.ts  按配置挑实现
│   │   ├── chatTransport.ts   传输层**接口**（唯一被允许描述网络的地方）
│   │   ├── prompts.ts         提示词与 JSON 契约；六角度补漏池也在其中
│   │   ├── sse.ts             SSE 流解析
│   │   ├── coerce.ts          容错读取：模型给的 JSON 缺字段、串类型也不崩
│   │   ├── review.ts          复盘正文的形状（五段）+ 解析 + 降级 + 跨周重复计数
│   │   ├── mergeReview.ts     重新复盘时的清单保护
│   │   ├── reviewEdit.ts      复盘编辑操作（只有清单可改）
│   │   ├── legacy.ts          0.8 旧结果的迁移：`WeeklyResult` → `Review`
│   │   ├── aiError.ts         失败翻译成人话
│   │   ├── week.ts            周的计算：周键、相对说法、月历格（纯函数）
│   │   ├── archive.ts         按周归档：原文与复盘、回存、挪周、近三周、统计（纯函数）
│   │   └── recency.ts         「多久以前」的说法：按流逝时间分档，与「今天是哪天」无关（纯函数）
│   ├── shared/        两边共用的契约。环境无关，所以主进程与渲染进程都能引
│   │   ├── ipc.ts             通道名与消息形状（三处共用同一份定义）
│   │   ├── chatStream.ts      响应怎么读：SSE 逐段 / 网关整段返回 JSON
│   │   └── bridge.ts          探测「有没有那座桥」，决定走哪条路
│   ├── host/          主进程侧的逻辑。纯 Node，**不 import electron**，所以能单测
│   │   ├── fileStore.ts       两个 JSON 文件：配置、周归档
│   │   ├── llmForward.ts      真正发请求的地方
│   │   └── llmService.ts      请求记账：增量往哪发、取消落到哪
│   ├── transport/     传输层**实现**：浏览器一份（fetch），主进程一份（IPC）
│   ├── storage/       本地留存：localStorage 一份，主进程 JSON 文件一份
│   └── ui/            页面
├── live/              真模型试跑台（试跑用的假原文与整场跑法）
│   └── review.live.ts         复盘流的真模型试跑台，见第六节；刻意不混进 npm test
├── build/
│   ├── icon.png       应用图标（256×256）
│   └── icon.ico       同一张图的 7 个尺寸（16/24/32/48/64/128/256），打包直接用
└── scripts/           构建、冒烟、图标生成（esbuild 打包主进程、启动冒烟）
```

依赖方向是单向的：`ui → core ← transport`，`electron → host → shared ← transport/storage`。
六条规则：

1. `core/` 里不许出现 React
2. `core/` 里不许出现网络与浏览器 API（`fetch` / `localStorage` / `window` / `document`）
3. `core/` 不许依赖 `transport/` 或 `storage/` 的具体实现，只依赖 `chatTransport.ts` 里的接口
4. `core/` 不许反向依赖 `shared/` 与 `host/` —— 契约不能往业务层倒灌
5. `host/` 与 `shared/` 里不许出现 React 与界面；`host/` 还不许 import `electron`，
   否则主进程逻辑就没法脱离壳单测了
6. `electron/` 里不许写业务：不发请求、不 import `core/` 的业务模块，只接线

**前三条由 M2 的测试强制，后三条由 M4 加进来**，都写在 `demo/src/core/layering.test.ts` 里。
它直接读源码检查越界，并逐个文件报出违规者。某个着急的下午想往 `core/` 里 import 一个
React hook 时，测试会拦住。

好处是具体的：全套用例里的绝大多数可以完全脱离界面与网络运行，24 个文件跑一次不到四秒；
连主进程那部分（落盘、转发、请求记账）也不需要启动 Electron，注入一个假的传输层就能测。

## 四、四个核心决策

### 4.1 网络调用收进传输层，而不是散在组件里

**问题**：浏览器直连 DeepSeek 这类接口会撞跨域。而「主进程发请求」是最终形态，
但 M2/M3 还想在浏览器里快速验证交互。

**决策**：把「发请求」抽象成 `ChatTransport` 接口，实现可以换：

| 阶段 | 实现 | 跑在哪 |
|---|---|---|
| M2 / M3 | `transport/browserTransport.ts`，dev 期经 Vite 代理 | 浏览器 |
| M4（已完成） | `transport/ipcTransport.ts`，主进程里由 `host/llmForward.ts` 真发请求 | Electron 主进程 |

**为什么不在组件里直接 fetch**：那样跨域、Key 位置、超时、流式解析会散在 UI 代码里，
M4 换外壳时等于重写网络层。

**M4 实际怎么做的**：新增 `transport/ipcTransport.ts` 实现同一个接口，再由
`transport/index.ts` 按「有没有那座桥」自动挑一份；`App.tsx` 只改了注入的那一行，
`core/` 一行没动，`ui/` 一行没动 —— 这正是当初留这道口子想要的结果。

增量通路也保住了：主进程每收到一段就推一次增量（`llm:delta`），带上请求标识。
v0.9.0 改成复盘流之后界面不再逐字显示（原因见 4.3），但这条通路连同它上面的 SSE 解析原样留着 ——
以后想换回任何「边收边显示」的形态，不用重接。

### 4.1b 主进程也写得很薄，是为了下一次换壳

`electron/main.ts` 里只有三件事：开窗口、接 IPC、读写文件。真正干活的三个模块
（`host/fileStore.ts`、`host/llmForward.ts`、`host/llmService.ts`）是纯 Node，
**不 import electron**，所以能在 vitest 里直接测，不需要启动浏览器窗口。

这条约束由测试强制（见分层约束第 5 条）。它防的是最自然的那个滑坡：
「反正 IPC 都在这儿，顺手把判断也写这儿吧」—— 一旦开始，主进程就会长成第二个业务层，
日后想换 Tauri 就得把逻辑再抄一遍。

### 4.2 一次调用得出整份复盘

**问题**：v0.9.0 之前是采访流 —— 每轮一次调用，靠行首 `[追问]` / `[换题]` 标记推进状态机。
改成复盘流之后，输入变成用户一口气写下的整周原文（`notes`），
要的是一份**结构完整的复盘正文**，不是下一句话。

**决策**：**一次调用返回整份复盘**。不是「先提炼再建议」的两轮，也不是逐段长出来。
模型交的是一份 JSON，契约字符串写在 `core/prompts.ts` 的 `REVIEW_SHAPE` 里：
`headline` / `did` / `issues[{text,key,advice}]` / `reconcile[{text,state,note}]` /
`plan[{text,when}]` / `nudge` / `reply`。

**为什么不再用行首标记**：标记是给「一次只产出一句话」的形态用的。
现在要的是七块字段互相咬合的一份东西，只有 JSON 能一次说清楚。

**模型给的 JSON 不合法怎么办**：这是整个改版里最需要兜住的地方。
`core/coerce.ts` 负责从模型输出里捞出那段 JSON（前后有多余的话、带 markdown 代码围栏、
字段缺失或类型不对都认），`core/review.ts` 的 `coerceReview` 再把它归成 `Review`。

**解析失败不抛**：`parseReviewSafe` 失败时**不抛异常、不中断流程**，退回
`degradedReview(reason)` —— 一份 headline 以 `这次没能整理成功：` 开头的占位复盘。
界面用 `isDegradedReview` 认它，命中时只把原因显示成错误，
**既不落盘、也不与已有复盘合并**。这条边界很重要：占位复盘本身没有任何信息量，
一旦写进归档，就会盖掉用户上一次真正整理出来的东西。

### 4.3 界面不再逐字显示流式，但增量能力留着

**问题**：采访流时代正文是纯文本，可以边收边显示。
复盘流的产出是 JSON —— **JSON 必须整份收完才能解析**，半截的花括号显示出来只是噪音。

**决策**：分析期间界面只显示一句「正在复盘这一周…」，不做逐字输出。
但 `ChatTransport.send(req, onDelta?)` 的 `onDelta` 参数、`shared/chatStream.ts` 与
`core/sse.ts` 那一整套流式解析**全部保留**，`AiClient.analyze(req, onDelta?)` 也照旧接受回调。

**为什么保留**：删掉它省不下什么，却把「换个形态再流式」的路堵死了。
现在的用法是「收增量但不显示」—— 增量仍然一段段到达，只是攒够整份才拿去解析。

### 4.4 清单归用户，判断归模型

产品文档 3.4 有一条明确约定：**重新复盘只重写判断，尊重用户手改的清单。**

复盘的五段分成两类，待遇完全不同：

| 段落 | 谁说了算 | 能不能手改 |
|---|---|---|
| `did`（做了什么）、`plan`（下周计划） | 用户 | 能：`core/reviewEdit.ts` 只提供 `setDid` / `setPlan` / `addPlan` / `updatePlan` / `removePlan` |
| `headline`（一句话）、`issues`（问题与建议）、`reconcile`（上周对账）、`nudge`（补漏提示） | 模型 | 不能：每次复盘重算，界面上不给编辑入口 |

**合并规则**在 `core/mergeReview.ts` 里：清单以用户手上那份为准，模型只能往里追加新内容；
判断项一律用模型这次的结果。所以「用户改过的一条计划」不会被下一次复盘冲掉。

**用户删掉的那一条也不会回来**：光看前后两份复盘，分不出「用户删了」和「模型这次没提」，
所以「删过什么」要单独记着 —— `core/reviewEdit.ts` 的 `droppedAfter(previous, next)` 比出这一轮
被删掉的文本，累加进 `WeekEntry.dropped`（按周存着，`storage/shape.ts` 归一化），
下一轮重新整理时 `mergeReview(current, fromModel, dropped)` 在追加之前把它们滤掉。
不传 `dropped` 的调用点行为一个字不变。

**这是旧版 `refineMerge.ts` 同一个决策的延续，不是新立的规矩。**
采访流时代的动机一模一样：模型重新整理时会顺手把用户改过的清单改回去，
而用户改的那一笔才是他真正认可的东西。当时做成「提示词层 + 代码层」两层保护；
现在提示词层不写了（整份重出，再写一句「原样返回」反而是让模型别动脑），
保护整个落在合并这一层 —— 一层就够，因为它不依赖模型配合。

### 4.5 跨周只对紧邻的上一周，靠 2–6 字的标签对齐

**问题**：周复盘的价值有一半在「上周说的，这周做了吗」。但归档会一直长下去，
拿哪几周喂给模型、怎么判断「这周说的这件事」就是上周那件事，都得先定死。

**决策**：

- **只取紧邻的上一周**：`archive.previousWeekContext(list, week)` 取 `addWeeks(week, -1)`，
  有就带上，没有就传 `null`。往前翻更多周不在这一版里。
- **上周给两样东西**：它的 `plan`（行动项）与 `issues` 的 `{text, key}`。
  模型据此产出对账的三段状态 —— `done`（做了）/ `partial`（做了一半）/ `unmentioned`（没提到），
  文案由 `RECONCILE_LABELS` 定。
- **issues 靠 `key` 跨周对齐**：每个问题带一个 2–6 字的短标签（比如「方案反复」），
  比对前先过 `normalizeKey`（去空白、去标点、转小写），所以模型换个说法、多打个空格也认得出。
- **重复次数由代码数**：`repeatCount(historyKeys, key)` 数的是「这周之前出现过几次」，
  数的是本地归档，不是模型说的。界面上那句「第 N 次出现」就是它。

**为什么用短标签，而不是让模型比对两段文字**：让模型判断「这两句话是不是同一件事」
既贵又不稳定，而且没法测。短标签是一个可以断言的东西 —— 用例里直接给两组 key 就行。

**为什么只对上一周**：「跟上个月比」是另一类问题（要重新设计上下文策略，见第九节），
和「上周说的做了吗」混在一起会让提示词和测试都糊掉。

### 4.6 按周归档：键用「那一周的周一」，一条记录 = 原文 + 复盘

**问题**：要能翻出旧周。而 v0.9.0 的输入是用户自己写的原文，
「这周的原文还留着吗」和「这周的复盘还留着吗」是两件事 —— 写了一周的话还没复盘，
下次打开应该原样在那儿，而不是逼用户重写一遍。

**决策**：归档文件 `weeks.json`，每条记录的键是**那一周周一的本地日期**（`2026-09-21`），
值的形状是 `{ week, savedAt, notes, review }`。`review` 允许是 `null`，
意思就是「只写了原文，还没复盘」。周的计算全部收在 `core/week.ts`。

四个具体取舍：

1. **不用 ISO 周号（`2026-W39`）**。跨年那几周是出了名的绕（第 1 周从哪天算起要单独定义），
   而且 `W39` 用户不认、排序还得再写一个比较函数。用周一日期当键则可排序、可相减，
   存档打开就能看懂。
2. **全程本地时间，一次都不碰 UTC**。用 `new Date(y, m, d)` 构造、用 `getDay()` 定位周一 ——
   晚上十一点存下来的东西被算到第二天（乃至下一周）去，是这类代码最常见也最难发现的错。
   跨夏令时的地方 `weeksBetween` 靠四舍五入兜住（一周的毫秒差可能少一小时）。
3. **原文自动落盘**：输入停下 `NOTES_DEBOUNCE_MS = 800` 毫秒就写一次，
   切周、离开页面、开始复盘之前各 `flushNotes()` 一次。**写原文也算「写入」**，
   会刷新这一周的 `savedAt`，所以总览页的「上次记录」会因为随手补两句话而往前跳。
   这是刻意的：那一栏问的就是「你上次动这个工具是什么时候」。
4. **存储从三个文件减到两个**：原来是 `config.json` + `session.json` + `weeks.json`，
   现在只有 `config.json` 与 `weeks.json`（见 `host/fileStore.ts` 的 `resolveStorePaths`）。
   **旧的 `session.json` 不做迁移**：0.8 一直是「会话 + 归档双写」，归档本身就是完整的，
   丢掉的只是「最近一次会话」这个冗余副本 —— 不值得为它写一段只在首次启动跑一次的代码。
   写入方式没变：仍然先写 `.tmp` 再 `renameSync`。

**读取与清理的规则一律在 `storage/shape.ts`**：week 不是合法周键就丢掉、
`notes` 不是字符串就置空、`savedAt` 不是有限数就补成现在、
**`notes` 空且 `review` 为 `null` 的条目直接丢掉**（别在归档里留空壳）、
同一周只留一条、倒序截到 `ARCHIVE_LIMIT = 260`。
挪周遇到目标周已经有记录时仍然拒绝，宁可不动，也不悄悄顶掉另一周的存档。

**旧档里的 `result` 字段在读取时就地转换**：`core/legacy.ts` 的 `legacyToReview` 把 0.8 的
`WeeklyResult` 折进新的五段 —— highlights 与 events 归入 `did`，pending 归入 `issues`
（没有建议、`key` 为空），nextFocus 与 nextFollowUps 归入 `plan`（`when` 为空）；
人际与物品两栏不迁（新的五段里没有它们的位置），headline / reconcile / nudge 留空。
就地转换，不写一次性迁移脚本。

**为什么把复盘正文抽成 `ui/ReviewBody.tsx`**：当天主页与总览页的周详情看的是同一份东西
（五段 + 编辑手感）。各写一份迟早会长歪，所以抽出来给两处共用：
`Props` 里带不带 `onChange` 决定它可编辑还是只读 —— 总览页看旧周时不传，于是只读。
`ui/JournalPage.tsx` 只保留页头、原文卡与分析按钮那一块。

## 五、开发期为什么必须有个代理

浏览器直连接口会撞跨域，这是已知的踩坑点。所以 `vite.config.ts` 里写了一个 dev-only
的代理插件（`apply: 'serve'`），浏览器请求 `/llm-proxy/chat/completions`，
由 dev server 代为转发。

**关键设计**：转发目标来自请求头 `x-llm-base`，而不是写死在配置里。
这样设置页里换成**任何** OpenAI 兼容接口都能用，不用改配置重启。

代理做了三件容易被忽略的事：

- 剥掉 `Origin` / `Referer` —— 避免上游做来源校验
- 剥掉 `Accept-Encoding` —— 否则 SSE 可能被压住，看不出流式
- 响应加 `Cache-Control: no-cache` 和 `X-Accel-Buffering: no`，并直接 `pipe`

**实测结果**（假上游每 60ms 吐一段，共 4 段）：

```
status: 200   content-type: text/event-stream
arrival times (ms): 109, 167, 231, 294, 357     ← 5 次分别到达
spread: 248ms                                    ← 与上游节奏吻合，没有被缓冲
上游收到: POST /v1/chat/completions model=fake-model auth=Bearer sk-**** origin=(none)
```

这条测量是必要的：代理把 SSE 攒起来一次性返回，是流式方案最容易翻车的地方，
而且症状隐蔽 —— 功能「能跑」，只是不流式了。

**代价**：这条链路只在浏览器 dev 模式下存在。打包后的应用由主进程直连接口，
Key 不经过任何本地代理 —— 这也是 M4 做完之后顺手消掉的一条。

### 真模型试跑台：`npm run try:model`

几百个用例能证明「管道通畅」，证明不了「模型理得像不像人话」。后者要真 Key、要花钱、
要联网，所以**刻意不放进 `npm test`**：它有自己的 `vitest.live.config.ts`，
include 只覆盖 `live/**/*.live.ts`，`npm test` 一行都不会碰到它。

它的分工是：用一份写死的假原文喂进去，把整条复盘链路真的跑一遍，
再把模型的原始回答、单次耗时、生成的那份 JSON 原样写进 `live-output/live-<时间>.md`。
**机械性质它断言**（有没有崩、JSON 解不解得开、五段是不是都在、跨周对账有没有用上上周的计划），
**质量留给人判** —— 报告末尾列着那几个问题，其中一条是产品文档的生死线。
Key 从应用自己的配置文件读（`%APPDATA%\ai-weekly\config.json`），
**不落进报告**，也不进版本库（`live-output/` 已忽略）。

**现状**：试跑台已跟着 0.9.0 迁到复盘链路上 —— `live/review.live.ts` 把两周原文各喂一次
（第一周不带上周，第二周带上第一周的计划与问题标签），`npm run try:model` 在这台机器上跑得通。
2026-10-02 跑过一次：2 次调用、平均 3.1 秒、都是完整可解析的 JSON、一次降级都没有；
两周的 `headline` 都不是清单的复印件（「你这周的时间大半耗在等人拍板和临时救火上，方案原地转了三版」
「你这一周被老王卡死，别的事全停下来陪他等」），第二周的对账判出 `done`（方案发出去了）
与 `unmentioned`（一个字没提体检），上周的 `[沟通]` 标签被照抄了下来。
它在采访流时代还赚回过一次成本：第一次跑就给出 34/34 的标记遵循率，
并直接照出「本周主线是清单复印件」这个产品层面最重要的问题 —— 那次修好的规则现在仍写在提示词里。
但**样本只有 2 次调用、1 个模型，够不上「已验证」**：第九节那几条风险仍然挂着。

### 启动冒烟：为什么它是必要的

打包之后最容易翻车的不是业务逻辑（那部分有几百个用例盯着），而是「窗口起来了、
页面是白的」，以及「桥在、处理器不在」。这两类问题的症状都很隐蔽：应用看起来启动了，
用起来才发现什么都干不了。

所以 `npm run smoke`（跑源码）与 `npm run smoke:packaged`（跑 `release/win-unpacked`
里那个 exe）都会真启动应用，然后跑四关：

1. **窗口 / 页面 / 桥** —— `loadFile` 路径对不对、预加载注入没有、`#root` 挂上没有
2. **存储** —— 真的存一次配置、读一次、再去主进程那边确认 `config.json` 确实写出来了。
   「桥在」只说明 preload 跑过了，不代表 `ipcMain` 那边注册上了
3. **周归档** —— 同一条路再验一遍 `weeks.json`（探针写的是 `{ week, savedAt, notes, review: null }`
   这样一条「只写了原文」的记录）。少注册一个 IPC 通道的症状正是「总览页永远是空的」，
   而启动时一点都看不出来
4. **一次真的走 IPC 的请求** —— 打一个必定连不上的本地地址。要的不是「能连上」，
   而是失败被翻译成人话，而且请求确实是从主进程发出去的。刻意不依赖网络才能稳定跑

它已经赚回成本了：第一次跑就抓到了 vite 默认输出绝对路径、`loadFile` 下全 404
导致的白屏。这个问题在浏览器里永远复现不出来。

用一次性的 `userData` 目录，不会碰到真实的配置与归档。
**装到 `mvp\ai-weekly\` 的那一份也真启动跑过一次**（同样用一次性 userData）——
「安装包装出来的东西能跑」和「win-unpacked 里的东西能跑」是两件事。

**没覆盖的**：没有驱动界面真的从原文走到复盘（那要按文字找按钮，脆而且收益低）。
复盘正文的解析、合并、编辑各有自己的用例集盯着。

**M7 期间额外做过一次「真浏览器里的点一遍」**（一次性探针，用完即删，没进版本库）：
用 Electron 真的加载打包后的页面，预置两份旧周数据，然后**点**开总览、点日历里的日期、
展开四栏、删一条、补一条，每一步都去 `weeks.json` 里核对。结论：切周、展开、
删除与补记都准确写回了那一周，别的周没有被碰，本周也没有被误写，控制台零告警零错误。
它验证的正是单测碰不到的那一段 —— `App.tsx` 里的接线。之所以没留成常驻测试：
它要靠文字找按钮，而按文字找按钮的测试会在改一个字之后失效，
维护成本高于它拦得住的问题。真正的兜底是 `HistoryPage` 的渲染冒烟加上存储层的用例。

| API Key 明文存在本机 | 个人工具可接受，但需知悉。实际落在 `%APPDATA%\ai-weekly\config.json`（实测；`%APPDATA%\AI周报\` 不存在）。路径取自 Electron 的 `userData`，而 app 名来自 `package.json` 的 `name`（本仓库是 `ai-weekly`），跟 electron-builder 里的 `productName`（只影响 exe 与快捷方式）无关 —— 这条原先写错了，2026-09-29 实测纠正 |

| **JSON 契约依赖模型配合** | 模型给出的东西不合契约时，解析退回 `degradedReview` 占位：这一次不出复盘，但**既不落盘、也不覆盖已有复盘**。最坏情况是白花一次调用，而不是把之前整理好的东西弄坏 |
| 复盘的判断项不给手改 | headline / issues / reconcile / nudge 每次重算，用户手上只留清单的编辑权。想改一句话的措辞只能重新复盘，而重算会连带改掉别的判断项 —— 这是刻意换来的：判断类内容一旦能手改，「模型算的」和「你改的」就再也分不清了 |
| `localStorage` 有容量上限 | 只在浏览器模式适用；打包版走 JSON 文件，无此问题。但归档现在连原文一起存，而原文比复盘大得多 —— 浏览器模式下比以前更容易撞上这条 |
| 二进制要从镜像站下 | 本机到 github.com 的 release 下载不通，`.npmrc` 里指了 npmmirror。换网络环境时删掉那两行即可 |
| 打包时直接复制 `node_modules/electron/dist` | `electron-builder.yml` 里的 `electronDist`。本机上默认流程的「解压后改名」稳定报 EPERM，这样做顺带省掉一次 150MB 解压 |
| 图标 | 已补：`build/icon.png`（256×256）与 `build/icon.ico`（16/24/32/48/64/128/256 七个尺寸）都由 `scripts/make-icon.mjs` **手写 PNG 与 ICO 编码**生成 —— 仓库刻意不带图形依赖，为一个图标装 sharp/canvas 不划算。脚本会把刚写出的字节解码回来抽点自检（角透明、气泡白、三个点、ICO 目录与内嵌 PNG 尺寸自洽），因为这些字节得靠代码证明，人眼在 CI 里看不到 |
| **打包不再让 electron-builder 转图标** | 原先 `win.icon` 给的是 PNG，由 electron-builder 另起一个 node 子进程跑 icons-bundle 的 `icon-tool.js` 转 ico。本机这个环境里**子进程分不到内存**：堆长到 5 MB 就 `FATAL ERROR: ... JavaScript heap out of memory`，放大 `NODE_OPTIONS`（`--max-old-space-size` / `--max-semi-space-size`）也没用，`npm run dist` 稳定挂在这一步。现在 `win.icon` 直接给手写的 `build/icon.ico`，打包全程没有额外的 node 子进程。验证方式：从 `win-unpacked\AI周报.exe` 里抽出图标资源，与 ico 的 32×32 那张逐像素比对，一致 |
| **本工作区里 Node 删不掉工作区内的文件** | 实测：在根目录、`dist`、`dist/assets`、`dist-electron`、`live-output` 和新建目录里各放一个探针，删除调用正常返回、文件依然在；只有系统临时目录能删。后果是 Vite 的 `emptyOutDir`（逐个 `rm` 且失败静默跳过）完全失效 —— 每构建一次就往 `dist/assets` 再堆一份，而 electron-builder 按 `dist/**` 全量打包，安装包里一直悄悄带着二十来份死文件。更坑的是它会让「在 asar 里按字符串查新代码在不在」这种验证被旧包骗过（已经被骗过一次：查「悬着」命中的是 9/19 的旧包）。对策：`vite.config.ts` 显式写 `emptyOutDir: true`（对正常机器有效），并加 `npm run check:dist` 把它变成响亮的报错；清理仍需 shell（`Remove-Item dist -Recurse -Force`） |
| 周归档最多留 260 周（五年） | 超出后丢最旧的。这份文件每次编辑整份重写，十年下来会变成几兆，而十年以前的周报不会有人翻。要更长就改 `core/archive.ts` 里的 `ARCHIVE_LIMIT` |
| 旧周的「记错周」只能前后挪一周 | 挪到目标那一周已有记录时会被拒绝（按钮是灰的），需要用户自己先处理那一周。刻意不做「自动合并」：两份周报被合并成一份，损失是不可逆的 |
| 归档里的原文是用户自己写的，不是对话 | 复盘只有一次调用，没有「当时的对话」这回事。所以旧的一周能看原文与复盘、能改清单，但没法拿当时更完整的过程重新生成 —— 过程从来就没有被记下来过 |
| 0.8 的 `session.json` 不做迁移 | 0.8 一直是「会话 + 归档双写」，归档本身是完整的，丢掉的只是「最近一次会话」这个冗余副本。代价是：如果某一周只写进了会话、从没进过归档，那份内容不会被找回来 |

## 九、尚未验证的风险

**2026-09-29 拿真模型体检过一轮采访流**（`npm run try:model`，deepseek-chat，
一整场 16 个主问题 + 追问 = 34 轮）；**2026-10-02 又拿复盘流跑了一轮**（试跑台迁到
`live/review.live.ts`，2 次调用、两周原文）。所以下面凡是标了「采访流上已测」的，
对复盘流都不成立；标了「复盘流上跑过一次」的，也只是**一次两调用的观察，不是结论**。

按重要性排：

1. **复盘提炼的质量** —— 复盘流上跑过一次，**看着对**，但样本太小。采访流时代这条问的是
   「追问落在细节上吗」，现在要问的是另一件事：`headline` 有没有给出判断、`issues` 的建议
   是不是落到明天能做的一步。当年留下一条线索：「本周主线」两轮都是清单的复印件
   （events 写过什么就换个说法再列一遍），按产品文档第十一节那正是生死线，
   于是改成「第一条必须是主线，后面几条只写清单里看不到的东西」，改完主线稳住了、
   支撑条仍不稳定。2026-10-02 的复盘流两轮 `headline` 都过了这一关
   （「时间大半耗在等人拍板和临时救火上」「被老王卡死，别的事全停下来陪他等」），
   `issues` 的建议也都是「周一上午直接给老王发一条…」这种当天就能做的一步。
   **还要盯的是**：`did` 会不会把原文原样搬一遍（两轮都贴原文措辞，可接受但没余量），
   以及长原文下 `headline` 会不会退化成清单 —— 复盘流只有一次机会，没有追问可以补救。
2. **JSON 契约的遵循率** —— 未验证。采访流上测的是行首标记，两次独立跑（32 轮 / 34 轮）
   都是 34/34、无标记 0 轮；那条数据搬不过来。复盘流要验的是：
   七块字段是不是都在、`issues[].key` 是不是真的给成 2–6 字、
   `reconcile[].state` 是不是只出现在 `done` / `partial` / `unmentioned` 里。
   这是新的生死线 —— 契约不成立，`coerceReview` 会把大半内容丢掉，
   而丢掉的东西只有当用户自己发现「我明明写了」。
3. **`response_format: json_object` 的兼容性** —— 复盘流上跑过一次（2026-10-02，deepseek-chat
   两次调用都返回完整、可解析的 JSON），采访流时代也测过。它依赖上游支持，
   换模型时这仍然是第一件要试的事。
4. **原文变长之后的表现** —— 未验证。采访流的上下文是 25~35 轮对话；现在是一整周的原文
   一口气进去，写得细的可能有几千字。要观察的是：模型会不会只读了前半段、
   把后半周的事整段漏掉，以及 `issues` 是不是只从最显眼的那一件事里出。
5. **跨周的 `key` 稳不稳** —— 未验证。`repeatCount` 数得准不准，全看模型下周会不会
   给同一个问题起同一个短标签。它这周写「方案反复」、下周写「方案来回改」，
   在归档里就是两条互不相干的记录，「第 N 次出现」永远数成 1。
   这一条只能拿连续几周的真数据看，一次跑不出来。
6. **旧归档折成五段之后好不好用** —— 未验证。`legacyToReview` 的映射有单测，
   但真实旧档里的 pending 条目五花八门。折出来的 `issues` 没有 `key`、也没有建议 ——
   这类条目下周不会被对账认出来，也不参与「第 N 次出现」。真实数据上跑过才知道要不要补。
7. **安装包只在开发机验证过** —— 装到别的 Windows 上是另一回事
   （缺 DLL、杀软拦截、非中文路径）。要真分发才需要管，本版不做。
