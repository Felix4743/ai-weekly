## 一、约束条件

先看实际环境，不猜：

| 约束 | 实测值 |
|---|---|
| Node | v24.9.0 |
| npm | 10.9.2 |
| Rust / cargo | **不存在** |
| 使用场景 | 个人自用、单机、一周用一次 |
| 目标平台 | 先桌面 |

三条硬约束决定了后面几乎所有的选择：

1. **没有 Rust 工具链** → Tauri 出局。省下的体积只在分发给他人时才值钱，而配置成本现在就付。
2. **个人自用、低频** → 不要账号、不要云同步、不要服务端。谁都不用在运维上花时间。
3. **产品成败在于「AI 问得对不对」**（见产品文档第十一节）→ 技术方案的首要任务是让这一步能最快迭代，而不是让架构好看。

## 二、选型总表

| 层 | 选型 | 为什么 | 放弃了什么 |
|---|---|---|---|
| 外壳 | Electron | 本机已有 Node 24，零额外环境；主进程可以写得很薄 | Tauri（缺 Rust 工具链） |
| 前端 | React 18 + TypeScript 5.6 + Vite 5 | 生态成熟、上手快、构建快 | Vue / Svelte（团队熟悉度没有优势） |
| 状态管理 | **不用库**，`useState` + `useRef` | 只有三个页面，一个 `App.tsx` 就管得过来 | Redux / Zustand |
| 网络层 | `ChatTransport` 接口 + 双实现 | 业务逻辑不直接碰网络，换外壳时上层不动 | 在组件里直接 `fetch` |
| AI 协议 | OpenAI 兼容 `/chat/completions`，SSE 流式 | 兼容 DeepSeek 等，换模型不用改代码 | 各家的原生 SDK |
| 结果校验 | 手写容错解析 + 代码层兜底 | 模型偶发不合法是常态，要的是「不崩」而不是「严格」 | zod（不是不行，是当前规模不值得） |
| 存储 | M2/M3: `localStorage`；M4: 主进程 JSON（配置 / 会话 / 周归档） | 个人工具，本地优先 | 数据库、云同步 |
| 测试 | Vitest | 与 Vite 同源，零配置 | Jest |
| 打包 | electron-builder（M4） | Windows exe 这条路上坑最少 | electron-forge |

**没有引入的依赖**：UI 组件库、CSS 框架、状态管理、请求库、校验库。全部用原生 + 手写，
换来的是 `node_modules` 只有 101 个包、构建产物 184 KB。

依赖方向是单向的：`ui → core ← transport`，`electron → host → shared ← transport/storage`。
六条规则：

1. `core/` 里不许出现 React
2. `core/` 里不许出现网络与浏览器 API（`fetch` / `localStorage` / `window` / `document`）
3. `core/` 不许依赖 `transport/` 或 `storage/` 的具体实现，只依赖 `chatTransport.ts` 里的接口
4. `core/` 不许反向依赖 `shared/` 与 `host/` —— 契约不能往业务层倒灌
5. `host/` 与 `shared/` 里不许出现 React 与界面；`host/` 还不许 import `electron`，
   否则主进程逻辑就没法脱离壳单测了
6. `electron/` 里不许写业务：不发请求、不 import `core/` 的业务模块，只接线

**前三条由 M2 的测试强制，后三条由 M4 加进来**，都写在 `demo/src/core/layering.test.ts` 里。
它直接读源码检查越界，并逐个文件报出违规者。某个着急的下午想往 `core/` 里 import 一个
React hook 时，测试会拦住。

好处是具体的：全套用例里的绝大多数可以完全脱离界面与网络运行，跑一次三秒上下；
连主进程那部分（落盘、转发、请求记账）也不需要启动 Electron，注入一个假的传输层就能测。

### 核心接口与状态机语义（0.9.3 的真实签名）

**领域类型**（`core/types.ts`）：

- `Dimension = 'probe' | 'reconcile' | 'event' | 'people' | 'thing' | 'growth'` —— 四个内容块 +
  两道流程里的小题（`probe` 状态追问、`reconcile` 上周对账，都是 `kind: 'step'`）。
  **0.9.3 起状态不再是块**（它进了开场那张打分卡，见 4.10）
- `Depth = 'deep' | 'mid' | 'fast'`；`TurnAction = 'followup' | 'next' | 'block'`
- `InterviewState = { active: Dimension | null; blocks: BlockProgressMap; stateDone: boolean;
  lowKeys: StateKey[]; depth: Depth | null }`，
  `BlockProgress = { asked; followUpCount; complete; freeTurns; covered: string[]; nudges }`。
  **0.9.5 起没有 `askIndex` 了**（块内没有题序，见 4.15）：`asked` 只用来防打转，
  `covered` 记「这一块聊到了哪几个要点」，`nudges` 记收尾补问了几次。
  `stateDone` 表示「开场那张打分卡交了没有」，`depth === null` 表示「还没定档」——
  两者都由**用户点击**推进，不是模型判断的
- `WeeklyState = { scores?: StateScores; note: string; followUp?: string }`：四项的分 + 一行备注
  + 一段追问小结（0.9.4 加的，可选）。0.9.1 时这里曾是四行文字（`body / mood / focus / growth`）；
  配套的是 `STATE_KEYS = ['mood', 'sleep', 'sport', 'diet'] as const`、`StateKey`、
  `StateScores = Partial<Record<StateKey, number>>`、`createEmptyState()` 与 `isStateEmpty(state)`
- `ChatMessage = { id: string; role: Role; text: string; dimension: Dimension; at: number }`：
  **`stateKey?: StateKey` 这个字段 0.9.3 已删**
- `WeeklyResult` **九个键**，对应结果页的九栏（`plan` 那一栏装 `nextFocus` + `nextFollowUps`；
  第九栏「反复出现」**不在这一份里** —— 它由 `core/trends.ts` 从归档现算，见 4.17）：
  `events / people / things / pending / growth / highlights / nextFocus / nextFollowUps / state`
- `InterviewContext = { lastWeek?: LastWeekPlan; lastWeekKey?: string; thisWeek?: ThisWeekSummary;
  stateScores?: StateScores }`：`thisWeek` 是 0.9.3 加的（开场复述本周已记的内容），
  `stateScores` 是 0.9.4 加的（状态追问要看得见分，**只读**）

**跨周线索**（`core/trends.ts`，0.9.6 新增；纯函数、**只读**归档，不参与写路径）：

- `previousEntry(archive, week)`：**严格早于**这一周的最近一条记录（同周与未来周都不算，归档乱序也不怕）
- `previousTag(week, previousWeek)`：相隔正好一周写「上周」，否则写「上一次」——
  用户可能隔了三周才回来，写「上周」就是撒谎
- `compareScores(current, prev, week)` / `compareText(row)`：结果页四项与页头概览后面那行小字。
  `delta` 只在两边都打过分的项上算；**这一周没打分的项返回空串**（界面上一个字都不显示，
  不是显示成「未打分」），上一周没分、这一周打了才写「上周没打分」
- `recurringPatterns(archive, upto, opts?)`：跨周重复的三类东西（未办 / 下周计划 / 提到的人），
  每组 `PatternGroup { kind, text, hits, weeks }`，`hits` 里**每周至多一笔**
- 三个旋钮：`PATTERN_MIN_WEEKS = 2`、`SIMILARITY_MIN = 0.5`、`PATTERN_WINDOW = 12`
- 相似度 = `normalizeText`（全角折半角、去标点空白、转小写）+ **字符二元组 Dice 系数**；
  **人名只按规范化后完全相等配**（走相似度会把「张总」与「李总」并成一个人，见 4.17）
- 它是**显示层的一层皮**：算错最多少显示一句小字，永远不碰存档 —— 判据是 `WeeklyResult`
  一个字没动、这一栏也不进导出（见 4.17）

**分数**（`core/stateScore.ts`，0.9.2 新增、0.9.3 改签名）：

- `SCORE_MAX = 5`；`coerceScore(value)` **只认 1–5 的整数**，`0 / 6 / 99 / 3.5 / '3' / null /
  true / NaN / {} / []` 一律当「没打分」—— 0 分和没打分在数据里是一回事（取消就是这个动作），
  其余是脏数据，宁可丢也不能写进结果里
- `coerceScores(value)` 只挑 `STATE_KEYS` 里的合法项；`hasAnyScore(scores)` 回答「到底有没有分」
- `withScore(scores, key, value)` 传 `undefined` 删掉这一项、且不改原对象
- **`attachState(scores: StateScores | undefined, note: string): WeeklyState`** —— 这是 0.9.3 的签名，
  **不再接收旧 state**（0.9.2 那个「拿旧 state 补分数」的 `attachScores(state, scores)` 已不再用于
  这个语义）。一项有效分都没有时**不写 `scores` 键**，并且会把旧分一起清掉 —— 这样「没打分」在新档与
  旧档里是同一种形状，读档和导出不用区分「空对象」和「没有键」
- `scoreText(3)` → `'3 / 5'`、`scoreText(undefined)` → `'未打分'`；`scoreSuffix(4)` → `'（4 / 5）'`、没分 → `''`；
  `scoresText(scores)` 把四项拼成一行（一项都没点就是空串）

**状态四项的文案**（`core/stateFields.ts`，0.9.2 新增、0.9.3 改口径）：`StateField { key, label, ask }`
与 `STATE_FIELDS`（心情 / 睡眠 / 运动 / 饮食，`ask` 形如「这周心情怎么样？」；0.9.3 去掉了 `placeholder`，
也换掉了「身体 / 情绪 / 精力 / 心智」那套旧名字）、`stateField(key)`。开场打分卡的四排星、结果页那四排星、
「复制全文」的小标题都从这一份读 —— 放 `core/` 而不是 `ui/`，就是为了不让「结果页叫运动、导出叫锻炼」
这种事出现。

**状态机**（`core/interview.ts`，纯函数）：

- `createInterview({ hasLastWeek })`：初始 `{ active: null, blocks, stateDone: false, depth: null }`；
  `hasLastWeek: false` 时把 `blocks.reconcile` 直接标成 `complete` —— 上一周没有记录就跳过对账
- `setStateDone(state, scores = {})`：用户在打分卡上按下「打好了，开始聊这周」时调用，
  顺便**定下低分项**（`lowKeys`，见 4.11）；没交卡之前 `nextStage` 一直返回 `{ kind: 'state' }`
- `setDepth(state, depth)` 由 `App.tsx` 的 `handlePickDepth` 调用；定了档才进块
- `nextStep(state, dim, action, { covered } = {})`：自由聊阶段（本块 `complete`）只把
  `freeTurns + 1`；`action === 'block'` → 记下报上来的覆盖并 `complete`；
  `action === 'followup'` 且没到档位上限 → `followUpCount + 1`；
  否则换方向 → `followUpCount` 归零、顺手记下 `covered`。**0.9.5 起不再有 `askIndex`**：
  「要点全聊到」或「`asked` 到 `MAX_TURNS_PER_BLOCK`」都会把它标成 `complete`（见 4.15）
- `planBlockEnd(state, dim)` / `nudgeBack(state, dim)`：**收尾对账**。模型说收尾之后，
  前者算出「还差哪几个要点、要不要补问」，后者把块退回未完成并记一次补问（见 4.15）
- `nextStage(state)` 返回**四态** —— `{ kind: 'state' } | { kind: 'depth' } | { kind: 'block'; dim } |
  { kind: 'done' }`，顺序是「`stateDone === false` → state」→「`depth === null` → depth」→
  「按 `SCRIPT` 找下一个没完、且**有要点**的块」→ done（没有要点的步骤直接跳过）
- `pointsFor(state, dim)` / `uncoveredPoints(state, dim)` / `currentPoint(state, dim)` /
  `currentPointNumber(state, dim)`：**要点**取代了 0.9.4 的 `mainQuestionsFor` /
  `currentQuestionSpec`（都已删）。要念成一句完整的话时用 `spoken(point)`（取 `anchors[0]`，
  只给演示模式、跳过与补问兜底用）
- `coveragePercent(state)` **只累加四个内容块**（`CONTENT_BLOCKS`）的**要点**（÷ `TOTAL_POINTS` = 12），
  状态追问与对账不计入
- **`stateKeyForAnswer(state)` 已删**（0.9.2 有）：它按状态块的 `askIndex` 算出「刚回答的这句该挂哪一排星」。
  0.9.3 状态不再是一段对话，这个函数与 `ChatMessage.stateKey` 一起消失了

**脚本与档位**（`core/script.ts`，0.9.3 整份重写）：

- 每题是一个 `QuestionSpec = { intent: string; examples: string[] }`：`intent` 是「要问到什么」，
  `examples` 是几个示例问法 —— **示例是意思，不是要念的台词**（0.9.2 及以前这里存的就是要念的句子）
- `SCRIPT` 顺序：上周对账 `reconcile`（单题 step）→ 事情 `event` → 人际 `people` →
  物品与支出 `thing` → 成长 `growth`。**状态不在 `SCRIPT` 里**（它在开场打分卡上）；
  0.9.3 把「心智」从状态里拆出来、改名「成长」，并且放到采访最后
- `CONTENT_BLOCKS` 只挑 `kind === 'block'` 的四块（事情 6 题 / 人际 4 题 + 可选 1 题 /
  物品与支出 4 题 / 成长 2 题），采访页顶部标签也只有这四个，「上周对账」不占标签
- **`TOTAL_MAIN_QUESTIONS = 16`** —— `CONTENT_BLOCKS` 的主问题之和。0.9.2 是 18（那时状态 4 题也在
  题库里），0.9.3 状态走了打分卡，主问题少掉那 4 题
- `DEPTHS` 三档：深度 20 分钟 / 中度 12 分钟 / 快速 5 分钟；
  追问上限 `FOLLOWUP_CAPS = { deep: 5, mid: 2, fast: 1 }`，`followUpCap(depth)` 在未定档时用
  `DEFAULT_FOLLOWUP_CAP = 2`。0.8.1 的 `MAX_FOLLOWUPS_PER_QUESTION` 已经删掉
- 主问题只作参考与兜底：换不换块由模型的 `[换块]` 标记决定，题库降级成提示词里的「要问到什么」清单

**标记协议**（`core/turn.ts` + `core/persona.ts`）：三个行首标记 `[追问]` / `[换题]` / `[换块]`，
`parseTurnReply` 摘掉标记、还原成 `TurnAction`；**没有标记一律回退 `'next'`**（宁可少追一次，
不能漏掉一个主问题）。`PROTOCOL_RULES` **0.9.3 起是五条**，新增的那条是「参考题目给的是**要问到什么**，
不是你该念的句子：用你自己的话问、别照抄示例、也别一周又一周用同一句」；它和另外四条
（只输出一句话、要问的那件事没答到就换个说法、中立不编造、160 字上限）与 `MARKER_RULE` 一起由
`buildInterviewerSystem(personaPrompt, { marker })` 拼在**人设之后**。

**提示词构建**（`core/prompts.ts`）：`buildOpeningPrompt` / `buildTurnPrompt` / `buildClosingPrompt` /
`buildSummarizePrompt(history, ctx)` / `buildRefinePrompt(history, current, note)`。
题库进提示词的形状是 `questionList` 的「N. 要问到：…（示例：「…」）」，追问池是 `poolBlock` 的
「说到才追，不硬问」；`buildOpeningPrompt` 的表头明写「参考题目（给的是**要问到什么**，不是要你念的
句子）」。对账的开场用 `lastWeekBlock(ctx)` 复述**上周原文**（`ctx.lastWeekKey` + 上周的 focus /
followUps），本周已经聊过时再由 `thisWeekBlock(ctx)` 复述**这周已有的记录**（见 4.10）；档位写进提示词
（`depthGuidance`），进度里明写「本题已追问 N 次，上限 cap 次」。`buildTurnPrompt` 里有一条硬规则：
**[换题] 之前先确认这一轮要问到的那件事真的答到了**，没答到就换个说法再问一次，不许跳过。

**结果 schema**（`core/prompts.ts` 的 `RESULT_SCHEMA` / `RESULT_RULES`）：八栏，其中 **`state` 已从
schema 里去掉**（模型压根不产状态），`growth` 是新增的一栏（「这周看了什么、听了什么、想通了什么」，
最多 3 条，规则明写**不要写成「做了什么」**，那是 `events` 的活）；`state` 由客户端补齐，
`RESULT_RULES` 里对应的一句话是「**状态（心情 / 睡眠 / 运动 / 饮食的分数与备注）不由你产出**：
那一段是用户在界面上自己点的，别在 JSON 里编这一项，编了也会被界面上的真实数据覆盖」。
`pending` 里若含上周承诺要带「上周说好的」字样；`highlights` 第一条必须是本周主线。
`buildRefinePrompt` 额外约定 `events / people / things / pending / growth` **五栏**里用户手改过的
必须原样保留，真正重写的是 `highlights / nextFocus / nextFollowUps` —— 代码层的第二道保险是
`refineMerge.ts` 的 `mergeRefined`（五栏只追加、不覆盖；`state` 整组照搬当前的，
**漏掉这一句，「重新整理」一次就把用户点过的星全洗光**）。

**旧档兼容**（`core/parseResult.ts` + `storage/shape.ts`）：`toState` 先读 `note`，**旧档没有 `note`
才**把老的 `body / mood / focus / growth` 四行文字并成一行备注（原话保留，不丢内容）；
`coerceResult` 读 `growth`，0.9.3 之前的会话没有这一栏就补成空列表；`normalizeSession` 走同一条路 ——
**分数不需要迁移**：`toState` 会读 `scores`，也认中文键 `评分` / `打分`，只有出现合法分数才写
`state.scores`；0.9.2 之前的档没有这个键，读回来就是「没打分」，与「点掉最后一颗星」是同一种状态。

## 四、核心决策

### 4.1 网络调用收进传输层，而不是散在组件里

**问题**：浏览器直连 DeepSeek 这类接口会撞跨域。而「主进程发请求」是最终形态，
但 M2/M3 还想在浏览器里快速验证交互。

**决策**：把「发请求」抽象成 `ChatTransport` 接口，实现可以换：

| 阶段 | 实现 | 跑在哪 |
|---|---|---|
| M2 / M3 | `transport/browserTransport.ts`，dev 期经 Vite 代理 | 浏览器 |
| M4（已完成） | `transport/ipcTransport.ts`，主进程里由 `host/llmForward.ts` 真发请求 | Electron 主进程 |

**为什么不在组件里直接 fetch**：那样跨域、Key 位置、超时、流式解析会散在 UI 代码里，
M4 换外壳时等于重写网络层。

**M4 实际怎么做的**：新增 `transport/ipcTransport.ts` 实现同一个接口，再由
`transport/index.ts` 按「有没有那座桥」自动挑一份；`App.tsx` 只改了注入的那一行，
`core/` 一行没动，`ui/` 一行没动 —— 这正是当初留这道口子想要的结果。

流式也保住了：主进程每收到一段就推一次增量（`llm:delta`），带上请求标识，
界面照旧逐字出现。

### 4.1b 主进程也写得很薄，是为了下一次换壳

`electron/main.ts` 里只有三件事：开窗口、接 IPC、读写文件。真正干活的三个模块
（`host/fileStore.ts`、`host/llmForward.ts`、`host/llmService.ts`）是纯 Node，
**不 import electron**，所以能在 vitest 里直接测，不需要启动浏览器窗口。

这条约束由测试强制（见分层约束第 5 条）。它防的是最自然的那个滑坡：
「反正 IPC 都在这儿，顺手把判断也写这儿吧」—— 一旦开始，主进程就会长成第二个业务层，
日后想换 Tauri 就得把逻辑再抄一遍。

### 4.2 一轮只发一次请求

**问题**：最初的设计是两次调用 —— 先问「要不要追问」，再问「下一句说什么」。
用假 AI 时看不出代价，接上真模型就是**每轮双倍延迟、双倍花费**。

**决策**：一次调用同时返回两样东西。做法是让模型在**行首**用一个标记表态
（0.9.1 起有三个：`[追问]` / `[换题]` / `[换块]`）：

```
[追问]
这件事哪一部分最花时间？
```

**为什么不用 JSON**：JSON 没法边收边显示。一上流式，用户就会看到半截花括号。
行首标记在头几个 token 内就收完了，摘掉之后正文照常逐字出现。

**标记还没收全怎么办**：`turn.ts` 里的 `stripMarkerForDisplay(text, final)` 会在
开头看起来还是「没收全的标记」时先返回空串按住不显示 —— 否则界面上会闪一下 `[追`。
收全或判定不是标记后立刻放行。

**模型不听话怎么办**：没有标记时**一律按「换题」处理**（`turn.ts` 回退成 `action: 'next'`）。这是刻意的偏向：
少追问一次只是损失一点深度，漏掉一个主问题才是产品层面的失效。
而且状态机本来就是覆盖的最终保证（见 4.3），所以这个降级是安全的。

### 4.3 覆盖归状态机，措辞归模型

如果让模型自己决定问什么，它一定会偏 —— 逮着一个话题聊十轮，漏掉一整块。

所以分工写死在代码里：

- **状态机**（`interview.ts`，纯函数）：保证每个区块的每个主问题都被问到，
  追问次数按档位定死（快速 1 / 中度 2 / 深度 5），到顶即换题，每个区块各记各的进度
- **模型**：只负责在当前这一问上怎么问得自然、怎么追问得深

**追问次数以状态机为最终裁判。** 模型可能说「要追问」但次数已到顶，
这时按换题处理 —— 否则「模型给的话术」和「状态机推进后的新状态」会对不上，
用户会看到一句追问、但界面已经跳到下一题了。

**但脚本问完不等于他想说的说完了。** 所以主问题问完之后，这一块进入自由聊：
状态机只记 `freeTurns`（不动 `askIndex`、不动覆盖率），输入框继续留着，
模型转去顺着他的话追问。这里刻意不让追问上限生效 —— 那个上限是防审讯的，
防的是 AI 逮着一个话题问十轮，不是防用户自己想说。第一版把「已聊完」当成
收工信号、顺手把输入框藏了，实际用起来就是「我想接着说，它不让我说」。

这条分工还有个副作用：`interview.ts` 可以不连 AI 完整单测（当前 741 个用例（36 个文件））。

### 4.4 清单保护做两层

产品文档 3.4 有一条明确约定：**重新整理只重写主线和下周计划，尊重用户手改的清单。**

模型不总是听话，所以做两层：

1. **提示词层**：`prompts.ts` 明确要求 `events / people / things / pending / growth` 五栏清单原样返回，只能追加新内容
2. **代码层**：`refineMerge.ts` 以用户改过的版本为准合并 —— 清单顺序和内容一律保留，
   模型只能往里追加它新发现的内容（`state` 更严：整组照搬当前的，模型连碰都不碰）；
   主线和计划才用模型重写的结果

第二层才是可靠的。第一层只是让模型少犯错。

**0.9.3 起 `state` 这一栏整组都不许模型碰。** 模型返回的对象里压根没有 `state`（`RESULT_SCHEMA`
里已经把它去掉），`mergeRefined` 合并时写的是 `state: attachState(current.state.scores,
current.state.note)` —— 分与备注整组照搬用户当前的，连「只补空缺」都不做了。护的仍然是同一个理：
用户亲手给的东西，模型没有资格覆盖它。

### 4.5 语气交给用户，协议不交

**问题**：采访语气写死在 `prompts.ts` 的 system prompt 里，但每个人想要的陪聊方式不一样。
最彻底的做法是把整段 system prompt 开放给用户改 —— 那也就把手艺和电路焊在了一起。

**风险**：那段提示词里混着两类东西，地位完全不同：

| 内容 | 属于谁 | 改坏了会怎样 |
|---|---|---|
| 说话口气、要不要接话、话长话短 | 用户 | 只是不好听，改回去就行 |
| 行首 `[追问]` / `[换题]` / `[换块]`、一次只问一件事、不许编造、长度上限 | 程序 | 标记没了 → 流式界面闪出半个标记，状态机失去推进依据；一次问十件事 → 用户不知道该答哪个 |

**决策**：拆开。`persona.ts` 存用户那份人设原文，`buildInterviewerSystem(persona, { marker })`
每一轮把两者拼起来，**协议永远在后**，并且明写「人设里怎么写都不能违反」。
设置页能编辑的只是前半段，四套预设也不过是往编辑框里填一份起点文案。

**为什么不做成「预设编号 + 几个参数」**：那样用户只能在这四套里挑，也就谈不上专属。
存完整原文还有个好处 —— 以后加预设、改预设，用户自己写的那份不会被悄悄顶掉。

**一个实现细节**：`PersonaConfig.preset` 只用来决定界面上高亮哪一套，读取时一律由原文重新推导
（`matchPersonaPreset`），不采信存下来的值。否则就会出现「界面显示温和朋友、
实际发出去的是另一段」这种对不上的状态。

### 4.6 按周归档：键用「那一周的周一」，不用 ISO 周号

**问题**：`session.json` 只留得住「最近一次」。而「上周到底在忙什么」是做周复盘时最想知道的，
总览页要能翻出旧周，就必须先把每周的结果留下来。

**决策**：新增第三份文件 `weeks.json`，每条记录的键是**那一周周一的本地日期**（`2026-09-21`），
值的形状是 `{ week, savedAt, result }`。周的计算全部收在 `core/week.ts`。

三个具体取舍：

1. **不用 ISO 周号（`2026-W39`）**。跨年那几周是出了名的绕（第 1 周从哪天算起要单独定义），
   而且 `W39` 用户不认、排序还得再写一个比较函数。用周一日期当键则可排序、可相减，
   存档打开就能看懂。
2. **全程本地时间，一次都不碰 UTC**。用 `new Date(y, m, d)` 构造、用 `getDay()` 定位周一 ——
   晚上十一点存下来的东西被算到第二天（乃至下一周）去，是这类代码最常见也最难发现的错。
   跨夏令时的地方 `weeksBetween` 靠四舍五入兜住（一周的毫秒差可能少一小时）。
3. **`core/week.ts` 与 `core/archive.ts` 都是纯函数**。「周日算哪一周」「同一周改十遍只留一份」
   「挪周时目标已有记录就拒绝」这些规则，不启动界面就能测（当前 741 个用例（36 个文件））。

**写入时机**：结果一变就写两处 —— `session.json`（刷新不丢）与 `weeks.json`（总览看得到）。
两处都在 `commitResult` 这一个入口里，因为它就是「结果变了」的唯一入口；散出去必然漏一处。

**这一份属于哪一周**：生成结果的那一刻定下来（`weekKeyOf(new Date())`），存在 `resultWeek` 上，
之后编辑、重新整理都跟着它走；从存档恢复时用的是会话里存的 `week`。
不这么做的话，打开一份旧结果改两笔，就会把它悄悄记到本周名下。

**旧版本升级怎么办**：M7 之前只存过「最近一次会话」。首次启动时如果 `weeks.json` 不存在
而 `session.json` 里有结果，就按它的 `week` 补录一条 —— 而且**只在归档为空时做这一次**，
否则以后每次启动都会把用户删掉的周又冒出来。旧会话没有 `week` 字段，按 `savedAt` 推。

**回存的规则**：改旧周走 `updateWeekResult(list, week, result)`，写回**同一个 week 键**；
那一周不存在时原样返回，不凭空造一条。挪周（`moveWeek`）在目标周已有记录时**返回原列表**：
宁可不挪，也不能悄悄顶掉另一周的存档 —— 界面上那个按钮这时是灰的。

**为什么把结果页的正文抽成 `ui/ResultBody.tsx`**：总览页的周详情要看的是同一份东西
（七张清单卡 + 主线 + 下周计划，也就是结果页那九栏 + 一样的折叠手感）。各写一份迟早会长歪，所以抽出来给两处共用，
`ResultPage` 只保留页头、吸顶目录、导出与「重新整理」那块 —— 折叠状态仍由各自的页面持有，
因为结果页的目录跳转需要「跳到收起的那一栏时先展开」。

### 4.7 0.9.1 采访流：状态先行、档位由按钮定、对账只问一题

三个改动都是产品口径，落到代码里各只有一处：

1. **「状态」块排最前，也进结果** —— 当时 `SCRIPT` 的第一项就是 `mood`，`App.tsx` 的
   `startInterview()` 直接 `openBlock(createInterview(...), 'mood')`。结果从七栏变八栏（新增
   `state`），结果页对应多出第五张卡「状态」（`ui/CollapsibleCard.tsx` 的可折叠清单因此是五栏；
   **0.9.3 加了「成长」之后是六栏**）。
   四项**只存文字、不打分** —— 当时的口径是「打分只有等以后做出趋势页才值钱」，
   所以 `WeeklyState` 的注释里留了以后加 `scores?` 的位置；0.9.2 把这个位置真的填上了（见 4.8）。
   **0.9.3 已改：状态不再是「块」、`Dimension` 里也没有 `mood` 了，它变成开场一张打分卡（见 4.10）。**
2. **三档深度由客户端三个按钮定** —— 交完打分卡、`nextStage` 返回 `{ kind: 'depth' }` 时，
   `ui/ChatPage.tsx` 渲染 `DEPTHS` 的三个按钮；点哪个就走 `App.tsx` 的 `handlePickDepth` →
   `setDepth` → `nextStage` → `openBlock`。档位不交给模型判断：它是后面所有追问次数的输入端，
   由用户点击产生，确定性、可单测；每档的分钟数与追问上限都写在 `core/script.ts` 的 `DEPTHS` 里。
3. **「上周对账」是一道单题，不是一块** —— `Dimension` 里的 `reconcile` 带 `kind: 'step'`、
   只有 1 道主问题，真问法由 `core/prompts.ts` 用 `ctx.lastWeek` 现场拼；上一周没有记录时
   `createInterview({ hasLastWeek: false })` 直接把它标成 `complete`，采访里跳过这一步，
   覆盖率（`coveragePercent`）也不含它。

**分数与量化当时就说好不做**，归入「以后功能」；所以 0.9.1 的结果里一个数字都不存。

### 4.8 0.9.2 状态打分：分数只能从界面上点出来

**问题**：4.7 那一版把「分数与量化」整个归入「以后功能」。0.9.2 只做其中最轻的一块：
四项各配一排 0–5 星，用户自己点；趋势、对比那些仍然不做。

**为什么现在做**：用户 2026-10-03 的要求原话是「我想在状态栏直接给出一个评分系统，0-5 颗星用户点击就量化状态」
（澄清时又指定：四项各点一次、采访里点完结果页还能改）。要的是**点一下就替他把状态变成数字**，
不是让模型替他打分 —— 所以这一版只给「点击产生分数」，趋势与周与周对比继续留在「以后功能」。既然要做，
最要紧的一条是**谁能写这个分数**。

**决策：模型一个字都碰不到分数**。`core/prompts.ts` 里根本没有 `scores` 字样（0.9.3 起连 `state`
都不在 `RESULT_SCHEMA` 里了），`RESULT_RULES` 反而明写着「状态（四项分数与备注）不由你产出，
编了也会被界面上的真实数据覆盖」。分数的唯一来源是 `ui/StateScore.tsx` 的点按，`App.tsx` 在
`runSummarize` 里用 `attachState(stateScoresRef.current, stateNoteRef.current)` 拿界面上的真实数据
补出 `state`（0.9.2 的写法是 `attachScores(r.state, stateScoresRef.current)` 去**覆盖**模型产出的
state —— **已改名，语义也变了**）。理由很直接：模型说「这周身体 4 分」和我们想问用户的是两件事，
一旦让模型也写，屏幕上就再也分不清这个数字是用户点的还是它编的。

具体几个取舍：

1. **0 分不存在，「取消」就是再点同一颗**。`StateScore` 点第 N 颗 → `onChange(N)`，再点同一颗 →
   `onChange(undefined)`；`coerceScore` 因此只认 1–5 的整数，`0 / 6 / 99 / 3.5 / '3' / null / true /
   NaN / {} / []` 一律当「没打分」。数据里少一种状态，界面、存档、导出就少一处分叉 ——
   0 分和没打分在数据里本来就是一回事，与其编一个「0 分」的语义，不如让它压根不存在。
2. **没打分就不写 `scores` 键**。`attachState` 一项有效分都没有时返回的对象里**没有** `scores`
   （并且顺手把旧分清掉）。这样「没打分」在新档和 0.9.2 之前的旧档里是同一种形状，
   读档、导出、深拷贝都不用区分「空对象」和「没有键」，**旧档也不需要迁移**：
   `parseResult.ts` 的 `toState` 会读 `scores`（也认中文键 `评分` / `打分`），有合法分才写进去。
3. **重新整理必须把分显式带过去**。`refineMerge.ts` 的 `mergeRefined` 合并时写的是
   `state: attachState(current.state.scores, current.state.note)`：分与备注整组照搬当前的
   （0.9.2 写的是 `attachScores({ ...四项文字... }, current.state.scores)`，**已改名**）。
   这一句是最容易漏的坑 —— 模型返回的 state 里没有分数，只要顺手用模型的 state 一覆盖，
   用户点过的星就被「重新整理」一次洗光，而且当场看不出来。
4. ~~**星星挂在哪条回答下面，是数据说的**~~ —— **这条 0.9.3 已删**。0.9.2 用
   `ChatMessage.stateKey?: StateKey` 记下这条回答说的是四项里的哪一项，由 `interview.ts` 的
   `stateKeyForAnswer` 按 `askIndex` 算出当前该挂哪一排星；0.9.3 状态改成开场一张卡之后，
   `stateKey` 与 `stateKeyForAnswer` 一起删掉了（见 4.10）。
5. **一份文案定义三处用**。`core/stateFields.ts` 的 `STATE_FIELDS`（0.9.3 起是 `key / label / ask`，
   `placeholder` 已删）同时供开场打分卡那四排星、结果页那四排星、「复制全文」的小标题。
   放 `core/` 而不是 `ui/`，就是为了不让「结果页叫运动、导出叫锻炼」这种事出现。
6. **分数也算「一条」，但只算在目录的计数里**（0.9.3 改的口径）。导出时状态一节遍历
   `STATE_FIELDS`：有点分 → `- 心情：4 / 5`，只写了备注而一项分都没有 → `- （无）` 加一行
   `> 备注`；而 `outline.ts` 的 `countSection(result, 'state')` 从 0.9.3 起是
   「点了几项分算几条 + 写了备注再加一条」—— 0.9.2 那时只数四行文字，**已改**。

**怎么测的**：`stateScore.test.ts`（`15` 例）盯着上面第 1、2 条（非法值当没打分、空分不写键且
清旧分）；0.9.2 那时 `chatPage.render.test.ts` 用 `renderToStaticMarkup` 验星星挂在哪条回答下，
**0.9.3 这份文件整份重写了**（见 4.10）。这里有个 React 的坑值得记：
**元素树走不到函数组件内部的按钮**（React 不会去调用它），所以结果页那层只能靠
`el.type === StateScore` 认出四排星；「点第 N 颗 / 再点同一颗取消 / `disabled`」这组规则另外**直接调用**
`StateScore(...)` 拿元素树来断言 —— 组件是纯函数，这么测反而更直。

### 4.9 0.9.2 提问文案重写：只改说话的方式，不碰电路

0.9.2 的另一半是**采访里问出口的话**。上一版的句子有三个毛病：

1. **一句话里塞两三问**：「这周睡眠、运动和吃饭怎么样？」「这周精力最好的时段在做什么？被什么打断最多？」
   —— 模型念出来像体检表，人也只会挑一句答。
2. **行话与书面词**：「消耗情绪」「输入」「边界被侵犯」「支出情况」「精力最好的时段」。
   这些词用户自己看着都要翻译一遍，何况脱口而出。
3. **话里带着评判**：「应该做但没做」「本可以更好」「为什么没做」。复盘本来就容易自责，
   问句里再叠一层「你应该」和「为什么」，人就只回一句「忘了」。

**决策**：这次只改说话的方式，不动结构。四条规矩 —— **一句只问一件事** · **用他会说的词** ·
**不问「为什么」，问「当时怎么样」** · **先给一个能让他立刻想起某件事的锚点**。落到三处：

- `core/script.ts`：主问题与追问池全部改口语，定档那三句（`DEPTHS.phrase`）保持。例如
  「这周睡眠、运动和吃饭怎么样？」→「这周身体怎么样？睡得够吗？」，
  「这周整体情绪怎么样？最消耗情绪的一件事是什么？」→「这周心情怎么样？有没有哪件事一直挂在你心上？」，
  追问池里「主要是被什么影响的？」→「你觉得是什么影响了它？」
  （**0.9.3 又往上改了一层：这些句子从「写死的台词」变成 `intent` + `examples`，见 4.10**）
- `core/prompts.ts`：引导语，顺手修掉一处自相矛盾 —— 两处写成「一次只说一句话、问一到三个小问题就好」，
  前半句禁止后半句放行，改成「一次只说一句话（问一到三个小问题也行），不要堆成一长串」
- `core/stateFields.ts`：星星旁边那句（「这周的身体，点个星？」→「身体这周几分？」）

**为什么敢说「没动电路」**：主问题条数没变（当时 `TOTAL_MAIN_QUESTIONS = 18`，状态 4 / 对账 1 /
事情 6 / 人际 4 + 可选 1 / 物与钱 4 —— 0.9.3 状态改走打分卡之后这个值是 **16**），协议还是那三枚标记，
`nextStage` 状态机、存档格式一个字都没改 —— 改的全是字符串。文案是提示词里的字，调整它不该动到电路；反过来说，真需要改状态机才能改文案，
那才是设计出了问题。

**验证**：真模型整场跑一遍，问出来的就是这批新句子 —— 模型发言 48 轮、**行首标记遵循率 48/48（无标记 0 轮）**
（0.9.1 那次是 44 轮 / 44 个标记）。跑测报告留在 `demo/live-output/`，不进版本库。
**这组数字属于 0.9.2**：0.9.3 把提问改成 `intent` + `examples`、又加了「要问到的没问到不许换题」
的硬规则，提示词整个变了一次。0.9.3 已经重跑（16 个主问题、33 轮、33/33 无标记 0 轮，见第九节与 4.10）。

### 4.10 0.9.3：状态打分卡 + 成长 + 措辞交模型 + 一周两次接着补

四件事在同一版落地，共同点是**都往「客户端定流程、模型只管说话」这个方向挪了一步**。

#### 状态从「一段对话」变成「开场一张卡」

**问题**：0.9.2 把星星挂在状态那四题的回答下面，但状态四题本身是模型问出来的 —— 问法随机、
顺序也随机，四项的分与四项的问法谁对应谁只有 `ChatMessage.stateKey` 知道，一旦错位
（模型少问一问、用户跳着答）就错挂；采访的开场还夹在「先聊状态」和「先定档」之间。

**决策：一进来先交一张打分卡，卡交完才定档、才进块。** `nextStage` 因此多了一态：
`stateDone === false` → `{ kind: 'state' }`（由 `core/interview.ts` 的 `setStateDone` 推进）。
卡上就是四排星（心情 / 睡眠 / 运动 / 饮食）+ 一个备注框 + 「打好了，开始聊这周」；
`App.tsx` 的 `startInterview()` **不调 AI**，直接把卡摆出来 —— 第一句话要等定档、开第一块才发。
这么定的三条理由：

1. **它是确定性流程，不该塞进不确定的对话里。** 哪四项、要不要打分、几分算数、什么时候算完，
   全是程序知道的事；让模型把这件事再复述一遍，只会多一条出错的路。
2. **模型不产分，就不存在「这个数字是谁写的」这个问题。** 分与备注都在界面上产生，进结果时由
   `attachState(scores, note)` 补成 `WeeklyState`；模型那侧连 `state` 都不在 `RESULT_SCHEMA` 里 ——
   4.8 那条「模型一个字都碰不到分数」在这一版走到了底。
3. **改分改备注立刻落盘。** 采访页与结果页共用 `ui/StateScore.tsx`：`ResultBody` 里点一颗星走
   `attachState(withScore(scores, key, value), note)`，改备注走 `attachState(scores, note)`，
   都当场写回结果 —— 没有「保存」按钮，也就没有「改了没生效」这种中间状态。

代价写在明面上：`ChatMessage.stateKey`、`interview.ts` 的 `stateKeyForAnswer`、「`STATE_KEYS` 与
`mood.mainQuestions` 等长」这条护栏全部删掉（状态不再是块），`Dimension` 里的 `mood` 也没了。
旧档不受影响：`WeeklyState` 的形状仍是 `{ scores?, note }`。

#### 「心智」从状态里拆出来，独立成「成长」放到最后

0.9.2 的 `state` 是「身体 / 情绪 / 精力 / 心智各一句」，打分时「心智」也被塞进同一排星里 ——
它跟心情睡眠不是一类东西。0.9.3 的处理：

- `Dimension` 加 `growth`，`SCRIPT` 末尾多一块「成长」（2 道主问题），`WeeklyResult` 多一个
  `growth: string[]`，结果页多一张独立的卡（`COLLAPSIBLE_KEYS` 从五栏变六栏），导出多一节
- **不打分。** 心情、睡眠、运动、饮食回答的是「这周怎么样」，一个 1–5 的刻度正好；
  「这周长了什么见识、想通了什么」是内容不是一个刻度 —— 给它打分等于逼用户在一件说不清的事上
  选数字，选出来的数也解释不了什么。所以成长只有文字，`ui/ResultBody.tsx` 那张卡的说明就写着
  「这周长了什么见识、想通了什么（不打分）」
- 旧档兼容：0.9.3 之前的存档没有 `growth`，`coerceResult` 补空列表；老 `state` 里那行「心智」的文字
  会跟另外三行一起并进新的 `note`（第三节「旧档兼容」），内容不丢

#### 提问只给意图，措辞交给模型

**问题**：0.9.2 把主问题一句句改口语了，改的却是**我们写的那些句子** —— 于是模型要么照念
（一轮又一轮同一句），要么自由发挥（当时没有任何要求）。用户自己动手改的那份文案评审稿里写得很
直白（`docs/采访提问-文案改进.md`）：「我只用改的情况举个例子，别跟个人机一样问，谁愿意聊？」

**决策：题库里存的不再是句子，而是 `QuestionSpec { intent, examples }`。** `intent` 是「要问到什么」，
`examples` 是几个示例问法；提示词（`questionList` 的「N. 要问到：…（示例：「…」）」、
`buildOpeningPrompt` 的表头）与 `PROTOCOL_RULES` 两处都写明**示例是意思不是台词、不要照抄、
也别一周又一周用同一句**。这么分的理由：

1. **我们真正能确定的是「要问到什么」。** 「这周睡得怎么样」这句话该怎么说，取决于上一句用户说了
   什么、这周他在忙什么 —— 那是模型每一轮都看得见、而我们写脚本时看不见的东西。
2. **写死的句子会老化。** 一句问法第一次听着自然，第二次就是录音。把句子降级成示例，模型就有空间
   换说法，而「到底有没有问到」仍然由 `intent` 卡住。
3. **只放开措辞，不放开结构。** 几个内容块、每块几题、追问上限、三枚标记、覆盖率一律没动 ——
   这次动的是 `script.ts` 里那几个字符串的**类型**，不是电路。
4. **再配一条硬规则。** `buildTurnPrompt` 写明：`[换题]` 之前先确认这一轮 `intent` 那件事真的答到了，
   没答到就换个说法再问一次，不许跳过。0.9.2 只说「问到效果为止」，这一版把它写成了换题的**前置条件**。
   演示模式与网络兜底仍然需要一句能念出口的话，所以留了 `spoken(spec)`（取第一个示例）。

#### 一周两次接着补：并集，而不是覆盖

**问题**：一周里聊过一次，过两天想起还有事没记，再点进来 —— 0.9.2 等于从头再聊一遍，生成的结果
会把本周已有的那份顶掉（除非用户自己先把内容抄下来）。

**决策**：`startInterview()` 读本周归档里已有的结果，做三件事：

1. **开场先复述。** `mergeWeek.ts` 的 `recapLines(result)` 把已有清单压成几行（`事情：…` / `人际：…` /
   `物品与支出：…` / `未办：…` / `成长：…` / `本周主线：…`，每类取前 1~3 条），塞进
   `InterviewContext.thisWeek`，再由 `prompts.ts` 的 `thisWeekBlock` 写成「这周他已经聊过一次了，
   今天是接着上次补（不是从头再来）……开场先复述一句，别把已经聊过的再问一遍」
2. **状态卡预填。** 已经点过的星与写过的备注直接带进打分卡，用户只补新想到的
3. **生成时并集。** `runSummarize` 把新结果与本周旧结果交给 `mergeWeekResult(fresh, previous)`：
   events / people / things / pending / growth **五栏并集去重、新的在前**（同一件事只留一条、用新写法），
   highlights / nextFocus / nextFollowUps **新一轮给了内容就用新的、新的是空的才留旧的**，
   `state` 整组以新一轮为准

**为什么是并集而不是覆盖**：两次聊的是同一周的两半，不是「第二版」。覆盖等于让用户为「补充」付出
重聊一遍的代价，而周报的价值恰恰是「这一周没白过」记录得完整 —— 少一条比多一条糟得多。旧的接在
后面而不按时间重排，是因为**先说的通常更重要**（人是顺着想起来的顺序说的）；`mergeWeekResult` 只保证
新的不丢、旧的也不顶掉新的。另外 `hasWeekContent(result)` 特意**不算状态分**：只点了四颗星、
一句内容都没聊，那不算「这周聊过」，不该触发复述与并集。

**「从头再聊一遍」为什么单独一个入口**：并集成为默认行为之后，用户仍然需要一个「这次我不想要上次
那些」的出口 —— 最典型的是上次聊跑偏了，或者那份记录根本不是这一周的。`startInterview({ fresh: true })`
跳过「找本周记录」这一步（不并旧记录、状态卡也不预填），入口是 `ChatPage` 底部的「从头再聊一遍」
按钮（`handleStartFresh`）。**默认接着补、显式才重来**：能自动做对的事不必问用户，但也不能拿走他
重来的权利。

#### 怎么测的

- **`core/mergeWeek.test.ts`（新文件，`14` 例）**：`mergeNewFirst` / `mergePeopleNewFirst` 的
  排序与去重（新的在前、同一件事只留一条且用新写法、人名当去重键、空串与空名字丢掉）；
  `mergeWeekResult` 的三类处理（`previous` 为 `null` / `undefined` 时**原样返回同一个对象**、
  五栏并集、主线与计划「新的优先、新空留旧」、状态整组以新一轮为准）；`recapLines` 的条数上限；
  `hasWeekContent`（**只点了状态分不算聊过内容**）。
- **`core/probe.test.ts`（0.9.4 新增，`12` 例）**：低分线是 2 星、**没打分不算低分**、
  脏分数（0 / 6 / 小数 / 字符串）一律不追、多项都低时按四项固定顺序排；每项都给出
  「要问到什么」加示例、且示例是问句；睡眠问「什么挡着」、运动问「时间能不能挤出来」；
  追问落点里不出现「为什么没做到 / 应该」这类评判；摊成题目时一项一道、顺序不变；
  `scoresLine` 只列点过的项、一项没点就是空串。
- **`ui/chatPage.render.test.ts`（0.9.2 整份重写、0.9.4 补了状态追问那一组，`12` 例）**：一进来是状态卡
  （20 颗星 = 四项 × 5 颗）、卡没交之前四个块标签全是 `disabled` 且页面上只有备注框那一个
  `textarea`、点过的分亮着、备注排在四排星下面、交卡之后卡片收起并出现三档按钮、进块后页面上
  不再有星、`busy` 时星点不动、「从头再聊一遍」三种状态下都在。
- **它踩的坑（值得记）**：`renderToStaticMarkup` 拿到的是一棵**元素树**，**React 不会去调用函数组件
  内部的实现**，所以「顺着树找 `<button>`」永远找不到 —— 只能靠 `el.type === StateScore` 认出那几排星；
  要断言「点第 N 颗 / 再点同一颗取消 / `disabled` 时点不动」，得**直接调用** `StateScore(...)` 拿它
  返回的元素树来看。0.9.2 那份渲染测试是围着「星星挂在刚回答的那条回答下面」写的（靠 `stateKey`），
  状态卡一改、那些断言全部失效 —— 这也是这次把它整份重写的原因。**教训：测「星星长在哪个位置」
  这种界面结构的用例，结构一改就得重写；测「点一下会传出什么」这种数据契约的用例，一行都不用动。**

### 4.11 0.9.4：打完分之后按打分追问 —— 分数从「不给模型看」改成「只读给它看」

用户的原话是「第一步打完分之后就没后续了……我想打完分之后才根据打分情况进行提问」，
举的例子是「睡眠不好是为什么」「运动不够是为什么可以挤时间吗」。

**推翻了 0.9.3 的一条约定**，这是这一版最需要说清楚的一处：

| | 0.9.3 | 0.9.4 |
|---|---|---|
| 提示词里有没有分数 | **没有** —— `core/prompts.ts` 里连 `scores` 这个词都不出现 | **有** —— `probeBlock(ctx)` 明写「他给自己打的分：睡眠 2/5 · 运动 1/5」 |
| 为什么 | 分数只由界面产生，模型碰不到就不会编 | 不问分数就问不出「睡眠 2/5 是为什么」 |
| 没变的那条 | 模型**写不了**分：`state` 不在 `RESULT_SCHEMA` 里，`attachState` 用界面上的真实点击覆盖 | 同上，一字未改 |

其余分工都沿用 0.9.3 的口径：

- **哪几项值得追由客户端算，不由模型挑**：`core/probe.ts` 的 `LOW_SCORE_MAX = 2`，
  只认 `coerceScore` 过的 1–5 分，**没打分不算低分**（「没点」与「点了 2 分」在数据上本就不同）。
  这个判定是纯函数，所以「阈值改了会怎样」不用起界面就能测。
- **题目不写死在 `SCRIPT` 里**：`probe` 那一条的 `mainQuestions` 是空数组，
  由 `interview.ts` 的 `mainQuestionsFor(state, dim)` 按 `state.lowKeys` 现算。
  `currentQuestionSpec` / `nextStep` / `answeredInBlock` 全部走这一个入口 ——
  否则会出现「状态机按写死的清单推进、提示词按分数提问」这种两边对不上的情况。
- **低分项在交卡那一刻定下来**（`setStateDone(state, scores)` 写进 `InterviewState.lowKeys`），
  不是每次现算：流程要据此决定问几道题、什么时候整步跳过，而之后在结果页改分不该把已经问过的追问倒回去。
- **没有低分项时这一步整步消失**：`setStateDone` 顺手把它标成已完成，
  `nextStage` 另外还会跳过「没有题目的步骤」—— 这一层是给手工拼出来的残缺状态兜底的，
  免得空步骤露在流程里（`mainQuestionsFor` 里那句 `s.lowKeys ?? []` 也是同一个理由）。
- **每项各有各的追问额度**：`nextStep` 换项时 `followUpCount` 归零，
  所以「两项低、中度档」= 每项最多 1 + 2 轮，而不是两项共用 2 次。
- **小结存成独立字段**：`WeeklyState.followUp`（可选）。不并进 `note` 是因为
  `note` 是用户自己写的字、小结是模型据追问写的 —— 混在一格会让「接着补」的第二轮
  把上一轮的小结原样再抄一遍，并且顶掉用户改过的那句。
  代价是 `attachState` 多了一个参数、**不传就等于清掉它**：`ResultBody` 的三处改法与
  `refineMerge.mergeRefined` 都必须把它带回来（漏一处，「重新整理」一次就洗掉，
  而且当场看不出来 —— 与 0.9.3 那次「星星被洗光」是同一类坑，这次提前写了用例）。

### 4.12 0.9.4：内存 —— 先量，再改，剩下的是 Chromium 的地板

用户问「这个程序是不是占的内存有点大了」。先量，别猜。装机版（0.9.3）空闲停在
开场状态卡时是 **4 个进程 / 296.1 MB 工作集 / 202.0 MB 私有**，而这个应用只是一问一答
的文本工具。同一台机器上把几种关法都量了一遍（`electron/main.ts` 的注释里也抄了一份）：

| 配置 | 进程 | 工作集 | 私有 |
|---|---|---|---|
| 默认 | 4 | 296.1 MB | 202.0 MB |
| `--disable-gpu` | 4 | 276.3 MB | 140.0 MB |
| `--in-process-gpu` | 3 | 260.4 MB | 199.0 MB |
| 两个都开 | 3 | 238.3 MB | 129.3 MB |
| 再 + `--enable-low-end-device-mode` | 3 | **235.2 MB** | **127.0 MB** |

于是取最后一行，落成 `main.ts` 里的三句（**必须在 `app.whenReady()` 之前**：
之后再设不生效，而失效时界面一切正常、只有内存悄悄涨回去，所以拿
`layering.test.ts` 钉住了顺序）。`--js-flags=--max-old-space-size=256` 量下来没有增益，没加。
本机实测（dev 构建）从 4 进程 296.1/202.0 变成 **3 进程 265.4/137.8**。

**应用层到底有没有在涨**，另外用工具量了 —— 新增 `demo/scripts/measure-memory.mjs`：
用 CDP 连进渲染进程读 `performance.memory`，`--walk N` 还能自己点完打分卡、定档、
再发 N 轮回答（React 受控组件走原生 setter + `input` 事件，否则输入框不认）：

```
时点                     JS 堆   DOM 节点  气泡  当前步骤
空闲（开场状态卡）        9.54 MB       98     0  选一块开始
点完三颗低分星            9.54 MB       98     0  选一块开始
交卡 + 定档之后           9.54 MB       57     1  状态追问
第 6 轮回答之后           9.54 MB      100    13  状态追问
```

结论：**JS 堆整场恒定在 9.54 MB**，DOM 只随「当前这一步」的消息线性长
（采访页本来就只渲染 `active` 那一块，切块会掉回去）。也就是说那 200 多 MB 是
Chromium 的地板，应用层没有可捡的漏 —— 真要再降一档只能换外壳（见 4.1b 留的口子）。
这个脚本顺带也成了「新功能在真实界面里到底出没出现」的验证手段：
0.9.4 的「状态追问」就是靠它确认的（`--walk` 的交卡 + 定档之后，当前步骤正是「状态追问」）。

### 4.13 0.9.5：「这题跳过」—— 不发请求，但必须把下一题亮出来

用户的原话是「我有很多问题是没有感觉的，可以加个没有按键」。拍板的口径是
**不调模型、直接推进到下一题，而且不留痕迹**（不要「（这题跳过了）」那种灰字）。

做法就是状态机走一步 `nextStep(state, dim, 'next')` —— 与模型给 `[换题]` 完全等价，
所以题目条数、追问计数、覆盖率一个字都不用改。三个值得记的点：

> 0.9.5 后半程改了这条：块内没有「题目条数」了，跳过改成**把当前这个要点记成聊到了**
> （`currentPointNumber` → `nextStep(..., { covered: [n] })`），否则下一个要点的锚点问法
> 会把同一句又问一遍。见 4.15。

1. **不发请求就没有新文本**。第一次跑真实界面（`npm run verify:skip`）时，跳过之后
   屏幕上一直停着上一题，看起来像点了没反应。所以这一跳要拿客户端那句参考问法顶上：
   `spoken(currentQuestionSpec(advanced, dim))` —— 与「模型什么都没说」时的兜底
   （`openAiClient.nextMessage` 末尾）是同一句，不是新造一套。代价写在第八节：
   跳过之后那一句是参考问法，不是模型自己组织的措辞。
2. **App 层没有单测**，而「点一下是不是真的推进了」正是这一版加的东西。整份 `App.tsx`
   至今没有测试文件，所以这次在 `scripts/measure-memory.mjs` 里加了 `--skip N`：
   用 CDP 按文字找到那个按钮、连点、把「当前这道题」打出来。实测
   状态追问（1 道）→ 事情：「这周主要在忙什么？」→「有没有本来打算做、最后没动的事？卡在哪一步？」
   →「这周有没有一个决定，你当时挺拿不准的？」，同块内跳过不再发请求。
3. **第一次跑抓到两个真问题**：跳过之后屏幕毫无变化（补了第 1 条）、以及 AI 回话期间
   按钮看着能点却没反应（`busy` 只表示遮罩，不包括 `typing`；改成 `disabled={busy || typing}`）。
   —— 这两个都不是单测能发现的，写下来当「为什么值得为它专门写个驱动脚本」的理由。

### 4.14 0.9.5：结果页重排 —— 层级倒挂

原来的顺序是六张清单卡在前、`highlights` 与 `plan` 排第 7、8 位。而按产品文档，
「本周主线」是这项目的**生死线**：它值不值得看第二遍决定项目做不做。把生死线埋在
一屏折叠卡下面，是自相矛盾的。0.9.5 改成：

```
本周主线 → 下周计划 → 事情 → 人际 → 物品 → 未办 → 状态 → 成长
```

实现上只动两处，且必须同时动（否则目录与滚动高亮会对不上）：

- `core/outline.ts` 的 `SECTION_KEYS` —— 它既是目录栏的顺序，也是 `activeSection`
  取「当前高亮哪一项」时 offsets 的顺序；
- `ui/ResultBody.tsx` 里那两块 `<section>` 的位置。

六张 `CollapsibleCard` 之间的相对顺序一个字没动，总览页因为复用 `ResultBody` 也一起变了
（那边的用例同步改了）。另外页头加了 `.result-brief`（只列打过分的四项星 + 主线首句），
星是 `<span class="star">` 而不是 `StateScore` —— 复用样式但不给 `onChange`，
免得概览变成第二个能改分的地方。`core/archive.ts` 抽了 `mainLineOf(result)`：
总览页卡片、页头概览、归档列表三处本来是同一个规则的三份实现。

**没动的东西**：导出 Markdown 的章节顺序（「复制全文」仍是 清单 → 状态 → 主线 → 计划）。
理由是那是给别人看的一份文档、从上往下读就是一份清单；而屏幕上的第一屏要回答的是
「这周到底怎么回事」。真要统一，改 `core/resultText.ts` 一处即可。

### 4.15 0.9.5（后半）：从「逐条过题」到「聊到就算」

用户的原话是「感觉这个问法还是太机械了」。他给的三种感受很具体：**措辞太书面、像念稿**；
**追问像从列表里挑的**；**不该问的题它还是问**。据此诊断出四个结构性来源 ——
都不是措辞问题，所以改的也不是措辞：

| 来源 | 原来是什么样 |
|---|---|
| 结构 | 每块 6 / 4 / 4 / 2 道主问题、**固定顺序**，`[换题]` 的语义是「这一题问到了」 |
| 提示词 | `[换题]` 之前必须先确认「这一轮要问到的那件事他答到了」，**不许跳过** |
| 题库 | 每题 `{ intent, examples }`，而且**整块清单一次性交给模型** —— 它看到的是一张考卷 |
| 追问 | 每块一个 4~6 条的追问池，按次数轮取（`currentFollowUpSpec`） |
| 协议 | 第一条写着「只输出你要说的那一句话……**不要前缀解释**」，把「接话」掐死了 |

**改法（B 方案）**

1. **12 个要点**取代 16 道主问题：事情 4 / 人际 3 / 物品 3 / 成长 2。`script.ts` 里
   `PointSpec { id, intent, anchors }` 取代 `QuestionSpec { intent, examples }`；
   `DimensionScript.points` 取代 `mainQuestions`，`followUps` / `optionalQuestions`
   整个删掉、改成一个 `digInto` 方向。**要点表没有顺序含义**，先聊哪个由模型定。
2. `BlockProgress` 的 `askIndex` 换成 `covered: string[]`（+ `nudges`）；
   `nextStep(s, dim, action, { covered })`；新增 `planBlockEnd(s, dim)` 与 `nudgeBack(s, dim)`
   作为收尾对账。`currentQuestionSpec` / `currentFollowUpSpec` / `answeredInBlock` /
   `questionsInBlock` 全部删除。
3. **覆盖只在 `[换块]` 那行报一次**（`turn.ts` 的 `parseCoverage`，认全角冒号、顿号、
   空格与重复号）。中途不报 —— 每轮都报等于给每句话加一道格式化作业，那正是要治的东西。
   `TurnReply` 因此多了 `covered: number[]`。
4. **收尾对账 → 提示用户，而不是自动补问**（这一条是被实测改过的，值得记）：
   最初的做法是「模型说收尾后，若覆盖不全就用缺的那个要点的锚点补问一句」，跑完真模型才发现
   这个前提是错的 —— **六个块里四个收尾时都缺要点**（见下表），于是「偶尔兜底」变成
   「每场都触发好几回」，而锚点原文正是用户嫌「像念稿」的句子，机械感以补丁的形式回来了；
   更麻烦的是模型有时**低估**覆盖（事情那块明明聊过「季度数据一直没腾出时间」，它只报 1,4），
   这种时候补问会去问一件已经聊过的事。所以改成人拍板：收尾时只记一笔缺口，
   在输入框上方给一条可点掉的提示（`ui/ChatPage.tsx` 的 `.missed-hint`），
   「接着补」走 `core/interview.ts` 的 `reopenBlock`（切开那一栏 + 退回未完成，
   **不算一次补问**），用户打的下一句话会让模型拿到正常的回合提示词、自己接上。
   `nudgeBack` / `MAX_NUDGES` 留着没删 —— 真要走「模型补问」那条路时它们还在。

   | 块 | 要点 | 模型报的覆盖 | 缺 |
   |---|---|---|---|
   | 状态追问 | 2 | 1 | 缺 2 |
   | 上周对账 | 1 | 1 | — |
   | 事情 | 4 | 1,4 | 缺 2,3 |
   | 人际 | 3 | 1,2 | 缺 3 |
   | 物品与支出 | 3 | 1 | 缺 2,3 |
   | 成长 | 2 | 1,2 | — |

   （同一场：27 轮、行首标记 27/27、**`[换块]` 报覆盖 6/6** —— 机制是通的，模型报得也诚实，
   它只是**收得早**。）
5. **一条覆盖都没报过时，按「没按格式报」处理，不补问。** 这两种在数据上都是空的
   （`covered` 为空），但意思完全相反：前者只是没按格式说，后者会让每个块都白补问两句、
   平白多出一次问答。没有信息就不替它下判断。
6. **三条兜底**：要点全聊到即算收尾（不必等模型开口，这一条兜住「跳过」与演示模式）；
   每块最多 10 轮（`MAX_TURNS_PER_BLOCK`）；补问满 2 次放行。
7. **协议反转**：从「不要前缀解释」改成**要求**先说一句接住对方的话（引他的原词、
   点一个具体细节）再往下问；整段上限 160 → 200 字。不评价、不说教、不替他下结论、
   不给建议这四条没动。
8. **诚实记账**：**模型会谎报覆盖。** 所以覆盖只当**进度**用，不当作「内容进不进结果」
   的依据 —— 结果是另一次调用从对话原文里归纳的。谎报最多让进度条虚高，不会丢内容。

**代价（也写进第八节）**：块内没有题序之后，「这一块聊完了没有」全靠模型说，
剩下的只是几条上界；模型要完全不按格式报覆盖，收尾对账这条链路等于不生效
（只剩 10 轮上限兜底）。这两条都是拿「可控」换「像聊天」，是这一版明确的取舍。

### 4.16 0.9.5（后半）：跨栏上下文 —— 从「各聊各的」到「都带上，但只作背景」

0.9.3 起 `formatTranscript(history, dim)` 会按 `dimension` 过滤，只把**当前这一栏**的
对话记录交给模型，注释写着「避免模型串台去聊别的块」。代价一直没人算过：
**进新一栏时它连对话原文都不带**（`buildOpeningPrompt` 里 `history` 只用来判断
「是不是整场第一句」），能看到的只有进度行（「事情（已聊完），人际（要点 0/3）」）。
于是那句「过渡要像聊天：可以提一句他刚才说的（或他打的分）再接上」只能靠它**硬编**——
真模型实测里它说「刚说到状态那会儿你打了个分，我记住了」，而它在人际那一栏既看不到
状态那栏聊了什么、也拿不到分数。用户的问题正是「它是不是每一栏新起一个上下文」。

改法（用户拍板「带上前面所有栏的完整对话」）：

- `formatTranscript(history)` **去掉 `dim` 参数**，整场按栏分组原样给；新增内部
  `transcriptBlock(history, dim)` 统一抬头与那句约束 —— 「别的栏已经聊过的**只作背景** ——
  现在只聊「X」这一栏，别再回头去问那些栏；但可以顺着对方前面说过的话往下接」。
- `buildTurnPrompt` 与 `buildOpeningPrompt` 两处都换成它（前者原来只给当前栏，后者什么都不给）。
- 另外把**轮数预算**告诉模型：回合提示词里写上「这一块已经聊了 N 轮，最多 10 轮」，
  并加一句「快到上限时先把还没聊到的要点问掉」。原因是实测里「人际」那一栏聊满了
  10 轮被客户端硬收掉（它没有 `[换块]`，所以连覆盖报告都没有）—— 上界不该是断头台，
  让模型自己配速更好。

效果（同一份真模型报告，各栏的开场白）：对账栏说「脑子替你加着班到一点多」（引状态追问）、
事情栏说「报价的初稿发出去了、张总还悬着、数据卡在三个系统之间」（引对账栏）、
人际栏说「跟供应商一次就谈成了，顺得跟改三版方案像两码事」（引事情栏）、
物品栏说「你妈那几通电话你用『忙』挡回去了」（引人际栏）、成长栏说「椅子这钱花得值」（引物品栏）。
—— 五栏全都在引前面栏里的原话，这就是「像在听」与「在念表」的分界。

**没动的那条**：仍然**不做跨轮的会话复用**（每次请求从零拼 system + user，不靠上游的
多轮状态）。整场 30 轮约两三千 token，deepseek 的上下文放得下。

### 4.17 0.9.6：把归档用起来 —— 上周对比 + 反复出现

**为什么是这一层**。归档（`weeks.json`）从 M7 起就在写，`WeeklyState.scores` 从 0.9.2 起就在存，
但在这之前它们**一个消费者都没有**：总览页能翻旧周，旧周里的分数却只是数字。
上一版的「已知代价」里明写着「除了决定追问、显示、存档与导出，仍然没有第二个消费者」——
这一版补的就是那一句。但只补最便宜的两件：**跟上次比**与**反复出现**；
趋势曲线与自动打分不做，因为「刻度怎么定、空缺的周怎么画」还没想清楚（产品文档第十二节）。

**新建 `core/trends.ts`，只读归档**。它不在 `App.tsx` 的写路径上，也不碰 `WeeklyResult`：
算错、算漏、算不出来，最多是少显示一句小字或者少列一组，不会污染存档。
所以它不需要「猜错就回退」那一套 —— 这是把风险放在显示层、不放在数据层的做法。

**「上一次」不等于「上一周」**。用户可能隔三周才回来（真归档里就有 2026-09-14 → 09-28
这样的空档），`previousEntry(archive, week)` 取的是**严格早于这一周的最近一条记录**、
不要求相邻；`previousTag` 据此决定那句话写「上周 3 ↑1」还是「上一次 3 ↑1」。
写「上周」而其实隔了两周，是那种没人当场发现、但看久了就不信的数字。

**没打分的那几项一个字都不写**。`compareText(row)` 在 `row.current === undefined` 时返回空串，
界面是「有内容才渲染那行小字」，不是「未打分」占位。这一条是拿真实截屏纠出来的：
原先四行里有两行挂着「上周没打分」，四行里两行是噪音（`trends.test.ts` 留了两条用例钉住）。
反过来，**这一周打了分、上一次没打**，那句「上周没打分」是有用的 —— 它是真的变化。

**反复出现认什么**。三类来源：`pending`（一直挂在未办里的）、`nextFocus`（计划里说了还没动的）、
`people`（连着几周提到的人）。每组 `PatternGroup { kind, text, hits, weeks }`，
`hits` 里**每周至多一笔**（同一周写了三遍不算三周），少于两周的不列（`PATTERN_MIN_WEEKS = 2`）。

**相似度用字符二元组 Dice 系数**。中文没有词边界，分词器又太重，二元组在「同一件事换个说法」
这个场景里够用：实测 `similarity('报价发出去', '报价发出去了') ≈ 0.89`、
`similarity('把报价发出去', '把简历发出去') = 0.4`，阈值取 `SIMILARITY_MIN = 0.5`。
比较前先 `normalizeText`：全角折半角、去标点空白、转小写。
**人名不走相似度**，只按规范化后完全相等配 —— 因为 `similarity('张总好', '李总好') = 0.5`
正好压在阈值上，「张总」与「李总」会被并成一个人。这是有意识放弃的覆盖：**宁可漏，不许错认**。

**只看最近 12 条记录**（`PATTERN_WINDOW`）。两两比较是 O(n²)，而归档上限 260 周；
更长的窗口既慢，也会把半年前那件事与这周并到一起 —— 那已经不是「反复出现」，是巧合。

**新增的第九栏不进结果文件**。`core/outline.ts` 的 `SECTION_KEYS` 里插了 `'pattern'`
（在 `pending` 与 `state` 之间），`countSection(result, key, patterns = 0)` 与
`buildOutline(result, patterns = 0)` 各多一个可选参数 —— 条数是**从归档算出来传进去的**，
不写进 `WeeklyResult`，也不进 `core/resultText.ts` 的导出（导出章节顺序一个字没动）。
理由：这一栏不是「这周记了什么」，是「这一周跟前面几周比出来的东西」；
写进周报存档等于同一个事实存两份，还会互相打架。

**验证**。`demo/src/core/trends.test.ts` 38 条用例（纯函数，不碰界面）；三个渲染测试跟着改到
九栏 / 七栏可折叠。另外给 `scripts/measure-memory.mjs` 加了 `--seed <weeks.json>`（把真实归档
拷进一次性 userData，**只拷进去、不写回来**）与 `--shot <目录>`，于是有了 `npm run verify:trends`：
塞进真实的 3 周归档跑一趟真界面 —— 认出三组重复（「AI周报从0.9继续推」计划→计划、
「把测试的事说清楚」计划→未办、「素材录制按原节奏走」计划→未办），睡眠那行写着「上周 1 ↑1」，
没打分的三项一行小字都没有。截屏留在 `demo/live-output/trends/`（不进版本库）。

## 五、开发期为什么必须有个代理

浏览器直连接口会撞跨域，这是已知的踩坑点。所以 `vite.config.ts` 里写了一个 dev-only
的代理插件（`apply: 'serve'`），浏览器请求 `/llm-proxy/chat/completions`，
由 dev server 代为转发。

**关键设计**：转发目标来自请求头 `x-llm-base`，而不是写死在配置里。
这样设置页里换成**任何** OpenAI 兼容接口都能用，不用改配置重启。

代理做了三件容易被忽略的事：

- 剥掉 `Origin` / `Referer` —— 避免上游做来源校验
- 剥掉 `Accept-Encoding` —— 否则 SSE 可能被压住，看不出流式
- 响应加 `Cache-Control: no-cache` 和 `X-Accel-Buffering: no`，并直接 `pipe`

**实测结果**（假上游每 60ms 吐一段，共 4 段）：

```
status: 200   content-type: text/event-stream
arrival times (ms): 109, 167, 231, 294, 357     ← 5 次分别到达
spread: 248ms                                    ← 与上游节奏吻合，没有被缓冲
上游收到: POST /v1/chat/completions model=fake-model auth=Bearer sk-**** origin=(none)
```

这条测量是必要的：代理把 SSE 攒起来一次性返回，是流式方案最容易翻车的地方，
而且症状隐蔽 —— 功能「能跑」，只是不流式了。

**代价**：这条链路只在浏览器 dev 模式下存在。打包后的应用由主进程直连接口，
Key 不经过任何本地代理 —— 这也是 M4 做完之后顺手消掉的一条。

### 启动冒烟：为什么它是必要的

打包之后最容易翻车的不是业务逻辑（那部分有全套用例盯着：当前 741 个用例（36 个文件）），而是「窗口起来了、
页面是白的」，以及「桥在、处理器不在」。这两类问题的症状都很隐蔽：应用看起来启动了，
用起来才发现什么都干不了。

所以 `npm run smoke`（跑源码）与 `npm run smoke:packaged`（跑 `release/win-unpacked`
里那个 exe）都会真启动应用，然后跑四关：

1. **窗口 / 页面 / 桥** —— `loadFile` 路径对不对、预加载注入没有、`#root` 挂上没有
2. **存储** —— 真的存一次配置、读一次、再去主进程那边确认文件确实写出来了。
   「桥在」只说明 preload 跑过了，不代表 `ipcMain` 那边注册上了
3. **周归档** —— 同一条路再验一遍 `weeks.json`。M7 加了两个 IPC 通道，
   少注册一个的症状正是「总览页永远是空的」，而启动时一点都看不出来
4. **一次真的走 IPC 的请求** —— 打一个必定连不上的本地地址。要的不是「能连上」，
   而是失败被翻译成人话，而且请求确实是从主进程发出去的。刻意不依赖网络才能稳定跑

它已经赚回成本了：第一次跑就抓到了 vite 默认输出绝对路径、`loadFile` 下全 404
导致的白屏。这个问题在浏览器里永远复现不出来。

用一次性的 `userData` 目录，不会碰到真实的配置与会话。
**装到 `D:\AI周报\` 的那一份也真启动跑过一次**（同样用一次性 userData）——
「安装包装出来的东西能跑」和「win-unpacked 里的东西能跑」是两件事。
（原先装在 `mvp\ai-weekly\`，2026-10-10 搬到工作区外：工作区里的可执行文件会被 DSH 的沙箱打上 Low 完整性标签，那样打不开。）

**没覆盖的**：没有驱动界面真的走完一轮采访（那要按文字找按钮，脆而且收益低）。
采访逻辑本身有全套用例盯着：当前 741 个用例（36 个文件）。

**M7 期间额外做过一次「真浏览器里的点一遍」**（一次性探针，用完即删，没进版本库）：
用 Electron 真的加载打包后的页面，预置两份旧周数据，然后**点**开总览、点日历里的日期、
展开清单卡（那时还是四栏，没有「状态」）、删一条、补一条，每一步都去 `weeks.json` 里核对。结论：切周、展开、
删除与补记都准确写回了那一周，别的周没有被碰，本周也没有被误写，控制台零告警零错误。
它验证的正是单测碰不到的那一段 —— `App.tsx` 里的接线（`commitArchive` → `saveArchive`）。
之所以没留成常驻测试：它要靠文字找按钮，而按文字找按钮的测试会在改一个字之后失效，
维护成本高于它拦得住的问题。真正的兜底是 `HistoryPage` 的渲染冒烟加上存储层的用例。

## 八、已知代价

| 代价 | 说明 |
|---|---|
| Electron 包体积：安装包 **107MB**，解包后 **374MB** | 实测值（Electron 44 + 我们的产物，没带 node_modules）。个人自用可接受；体积优势只在分发给他人时才值钱。其中我们的代码只有 ~200KB，剩下全是 Chromium |
| API Key 明文存在本机 | 个人工具可接受，但需知悉。实际落在 `%APPDATA%\ai-weekly\config.json`（实测；`%APPDATA%\AI周报\` 不存在）。路径取自 Electron 的 `userData`，而 app 名来自 `package.json` 的 `name`（本仓库是 `ai-weekly`），跟 electron-builder 里的 `productName`（只影响 exe 与快捷方式）无关 —— 这条原先写错了，2026-09-29 实测纠正 |
| dev 期（浏览器模式）Key 经过本地代理 | 同上；打包版由主进程直连，没有这条链路 |
| 行首标记依赖模型配合 | 靠「缺失即换题」降级兜住，最坏情况是少追问 |
| `localStorage` 有容量上限 | 只在浏览器模式适用；打包版走 JSON 文件，无此问题 |
| 二进制要从镜像站下 | 本机到 github.com 的 release 下载不通，`.npmrc` 里指了 npmmirror。换网络环境时删掉那两行即可 |
| 打包时直接复制 `node_modules/electron/dist` | `electron-builder.yml` 里的 `electronDist`。本机上默认流程的「解压后改名」稳定报 EPERM，这样做顺带省掉一次 150MB 解压 |
| 图标 | 已补：`build/icon.png`（256×256）与 `build/icon.ico`（16/24/32/48/64/128/256 七个尺寸）都由 `scripts/make-icon.mjs` **手写 PNG 与 ICO 编码**生成 —— 仓库刻意不带图形依赖，为一个图标装 sharp/canvas 不划算。脚本会把刚写出的字节解码回来抽点自检（角透明、气泡白、三个点、ICO 目录与内嵌 PNG 尺寸自洽），因为这些字节得靠代码证明，人眼在 CI 里看不到 |
| **打包不再让 electron-builder 转图标** | 原先 `win.icon` 给的是 PNG，由 electron-builder 另起一个 node 子进程跑 icons-bundle 的 `icon-tool.js` 转 ico。本机这个环境里**子进程分不到内存**：堆长到 5 MB 就 `FATAL ERROR: ... JavaScript heap out of memory`，放大 `NODE_OPTIONS`（`--max-old-space-size` / `--max-semi-space-size`）也没用，`npm run dist` 稳定挂在这一步。现在 `win.icon` 直接给手写的 `build/icon.ico`，打包全程没有额外的 node 子进程。验证方式：从 `win-unpacked\AI周报.exe` 里抽出图标资源，与 ico 的 32×32 那张逐像素比对，一致 |
| 人设由用户自己写 | 写得再离谱也只能影响口气：机器约定固定在提示词末尾，且有测试保证它排在人设之后。但「模型会不会照做」仍取决于模型 |
| **本工作区里 Node 删不掉工作区内的文件** | 实测：在根目录、`dist`、`dist/assets`、`dist-electron`、`live-output` 和新建目录里各放一个探针，删除调用正常返回、文件依然在；只有系统临时目录能删。后果是 Vite 的 `emptyOutDir`（逐个 `rm` 且失败静默跳过）完全失效 —— 每构建一次就往 `dist/assets` 再堆一份，而 electron-builder 按 `dist/**` 全量打包，安装包里一直悄悄带着二十来份死文件。更坑的是它会让「在 asar 里按字符串查新代码在不在」这种验证被旧包骗过（已经被骗过一次：查「悬着」命中的是 9/19 的旧包）。对策：`vite.config.ts` 显式写 `emptyOutDir: true`（对正常机器有效），并加 `npm run check:dist` 把它变成响亮的报错；清理仍需 shell（`Remove-Item dist -Recurse -Force`） |
| 周归档最多留 260 周（五年） | 超出后丢最旧的。这份文件每次编辑整份重写，十年下来会变成几兆，而十年以前的周报不会有人翻。要更长就改 `core/archive.ts` 里的 `ARCHIVE_LIMIT` |
| 旧周的「记错周」只能前后挪一周 | 挪到目标那一周已有记录时会被拒绝（按钮是灰的），需要用户自己先处理那一周。刻意不做「自动合并」：两份周报被合并成一份，损失是不可逆的 |
| 归档里只有结果，没有当时的对话 | 对话本身还没落盘（见第九节）。所以旧的一周只能看和改，不能拿当时的对话重新生成。这条边界来自「采访过程未落盘」，不是总览页自己的取舍 |
| 补录旧会话只在归档为空时做一次 | 否则每次启动都会把用户删掉的周又冒出来。代价是：如果归档非空、而会话属于一个归档里没有的周，那一次不会自动补录 |
| 状态四项的分数从 0.9.6 起有第二个消费者了 | 0.9.6 之前这一行写的是「除了决定追问、显示、存档与导出，仍然没有第二个消费者：没有趋势页、不做周与周对比」。现在**做了最便宜的那一半**：结果页四项与页头概览后面会写「上周 1 ↑1」（`core/trends.ts` 的 `compareScores` / `compareText`）。**模型依然写不了分、也依然不拿上一周的分说事** —— 对比完全发生在界面上，不进提示词。**仍然没做**的是趋势曲线与自动打分（刻度怎么定还没想清楚，见产品文档第十二节） |
| **关掉 GPU 进程与低配模式**（0.9.4） | 省下约 61 MB 工作集 / 75 MB 私有与一个进程（4.12 有实测表），代价是渲染走软件光栅与更小的缓存：这一页全是文字与少量过渡，实测看不出差别。真遇到滚动发涩，删掉 `main.ts` 里 `app.disableHardwareAcceleration()` 那一行即可，另外两个开关照留。**这句必须在 `app.whenReady()` 之前**，之后再加不生效、且失效时界面一切正常，只有内存悄悄涨回去 —— 所以 `layering.test.ts` 钉住了它 |
| 状态追问的小结多存一个字段 | `WeeklyState.followUp`（可选）。好处是它跟用户自己写的备注互不覆盖；代价是 `attachState` 从此有三个参数，**不传小结就等于清掉它** —— `ResultBody` 的三处改法与 `mergeRefined` 都必须带回来，漏一处「重新整理」一次就洗掉（0.9.3 那次「星星被洗光」是同一类坑，这次提前写了用例）。老档没有这个键，读回来就是空，不需要迁移 |
| **跳过之后那一句是参考问法，不是模型组织的措辞**（0.9.5） | 「这题跳过」不发请求（用户拍板的），可屏幕总得有下一题，所以用 `spoken(currentQuestionSpec(...))` 顶上 —— 与「模型什么都没说」时的兜底同一句。想让那一句也由模型说，就得为跳过再发一次请求，那是这个取舍的另一头 |
| 结果页的顺序与导出 Markdown 的顺序不一致（0.9.5） | 屏幕上是「主线 → 计划 → 七张清单」第一屏就给结论；`复制全文` 导出仍是「清单 → 状态 → 主线 → 计划」—— 那是给别人看的一份文档，从上往下读就是一份清单。两处各有各的理由，但**确实不一致**，改起来只需动 `core/resultText.ts` |
| **块内没有题序之后，「聊完了没有」全靠模型说**（0.9.5） | 客户端只剩三条上界：要点全聊到、每块 `MAX_TURNS_PER_BLOCK = 10` 轮、补问满 `MAX_NUDGES = 2` 次放行。好处是能跟着用户的话走、不再像表单；代价是模型要是一直不收尾，得等轮数到顶 |
| **模型可能谎报覆盖**（0.9.5） | 覆盖只当进度用、**不作为内容进结果的依据**（结果由另一次调用从对话原文归纳），所以谎报最多让进度条虚高。但它会影响收尾对账准不准：报得比实际多，就不会触发补问 |
| **模型完全不按格式报覆盖时，收尾对账等于不生效**（0.9.5） | `planBlockEnd` 对「一条都没报过」按「没按格式报」处理、不补问 —— 这是刻意的（那种数据与「一样都没聊到」完全一样、意思相反），但不报格式的模型就只剩 10 轮上限兜底 |
| **「是不是同一件事」靠字形相似度认**（0.9.6） | 字符二元组 Dice 系数、阈值 0.5。换个说法就配不上（「报价一直没发」与「报价还悬着」相似度不够），而一批同义句又可能配得过松。旋钮在 `core/trends.ts` 的 `SIMILARITY_MIN`。**宁可漏、不许错认**是有意的 —— 列错一条比少列一条更伤信任 |
| **人名只认同名**（0.9.6） | 「张总」「张总（甲方）」「老张」在反复出现里是三个人。改成走相似度的话，`similarity('张总好', '李总好') = 0.5` 正好压在阈值上，会把两个人并成一个。真要归并得先有一份人名表 —— 那是另一层 |
| **反复出现只看最近 12 条记录**（0.9.6） | 两两比较是 O(n²)，而归档上限 260 周。窗口再长既慢，也会把半年前那件事与这周并到一起（那不是「反复出现」，是巧合）。旋钮是 `PATTERN_WINDOW` |
| **跟上次比只有「上一次」一条线**（0.9.6） | 只有「上周 / 上一次 vs 这周」这一个对比，没有三周前、没有平均线、没有曲线。要画曲线得先定刻度与怎么处理空缺的周（见产品文档第十二节） |
| **「反复出现」不进存档、也不进导出**（0.9.6） | 它是从归档现算的视图，`WeeklyResult` 九个键一个字没动。好处是同一个事实不会存两份、也不会因为编辑旧周而互相打架；代价是**导出的那份 Markdown 里没有这一段** —— 把周报发给别人，对方看不到「这事你连着三周都没办」 |
| 结果页的目录跳转会先展开目标那一栏 | 收起来的卡跳过去等于跳到一个只有两个字的地方，所以 `ui/ResultPage.tsx` 不再自己列名单，改从 `ui/CollapsibleCard.tsx` 引 `isCollapsible` / `toggledCollapsed` —— 一份 `COLLAPSIBLE_KEYS` 说了算，加第六栏时不会漏（0.9.3 加「成长」那一栏正是从这份名单过的，一处没漏）。踩过的坑：`ResultPage.tsx` 原来另写了一份只列 `events / people / things / pending` 的实现，点目录跳到「状态」时不展开，看起来像坏了 |
| 一周里的第二次聊只能「并」，不能「替」 | 0.9.3 把「接着补」做成默认行为之后，想只保留这一次聊的内容就得手动删，或者在生成之前走「从头再聊一遍」。刻意没做「替换旧记录」这种开关：多一个开关就多一种用户要理解的模式，而周报的错法里「多带一条旧内容」远比「丢掉一条真聊过的内容」轻 |

   规矩，但「后期问得好不好」仍只有人工印象），但样本屈指可数、且是同一个模型，**还不算数**。

4. **`response_format: json_object` 的兼容性** —— 依赖上游支持。deepseek-chat 上实测
   可用：两次跑都返回了完整、可解析的 JSON（含 people 的对象数组），没有触发降级路径。
5. **安装包只在开发机验证过** —— 装到别的 Windows 上是另一回事

6. **用户自己写的人设是否被稳定遵循** —— 未验证。协议约定放在人设之后是工程上的兜底，

7. **「反复出现」的阈值只在 3 周真实数据上试过** —— 未验证。`SIMILARITY_MIN = 0.5` 与

   真归档只跑过一份 3 周的。归档攒到十周以上时，会不会漏得太厉害、或者把不相干的两件事并起来，
   只能等数据长出来才知道。要看效果不必等应用：`npm run verify:trends` 塞进真归档跑一趟，
   报告里直接列着这次认出来的那几组。
