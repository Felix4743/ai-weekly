## 一、一句话定位

> 周末坐下来跟 AI 聊五分钟，得到一份属于自己这一周的总结，和下周的计划。

---

## 二、要解决的问题

**问题不在「整理」，在「没有东西可整理」。**

目标用户平时不写周报、不做记录。到了周末想复盘，打开一个空白输入框，脑子里一片空白，写两行就关掉，此后再也不打开。

| 常见做法 | 为什么不行 |
|---|---|
| 给一个输入框让他写 | 没有素材，直接卡死 |
| 做一个记录系统让他平时记 | 要改变习惯，成本高，而他本来就不记 |
| 做统计图表 | 没有数据，图表全是空的 |

**结论：不要让他「想起来」，只要让他「回答」。**

回答一个问题，比凭空回忆容易十倍。

## 三、核心设计

### 3.1 AI 来采访你，而不是你对着空框写

打开软件，AI 先开口问一个问题；你随口答，AI 顺着追问。你只需要回答，不需要组织语言，也不需要先想好要写什么。

### 3.2 分块采访：四个词摆在顶上，点一下整页切换

采访内容分为四个区块：**事情 / 人际 / 物品 / 状态**。

这四个词**并排放在界面顶部**，点哪一个，整个对话区就切到哪一块：

- 每个词上带状态：未开始 / `1/4` / `✓`
- 对话区是一整页，只显示当前这一块的问答
- **发送按钮下面另有一排「聊一聊人际」这样的入口**，不用回到顶部就能换一块
- 一块的主问题聊完，按钮变成「接着聊『物品』→」，一键跳过去
- 四块都聊完（或用户中途想收工），点「生成我的本周梳理」

这样做的理由只有一个：**被人牵着走的对话，一旦用户对当前话题没兴趣，整场就断了。** 让他自己掌握进度，他才愿意多待一会儿。

> 曾经试过把四块做成同屏的折叠卡片，体验很差 —— 卡片展开后对话区被压得很扁，还要在一屏里同时看四摊东西。改成整页切换后，注意力只在一个地方。

### 3.3 状态机管覆盖，AI 管对话

**这是本产品最重要的一个设计决定。**

如果让 AI 自己决定问什么，它一定会偏——逮着一个话题聊十轮，漏掉一整块内容。

所以两者分工：

- **应用（状态机）**：保证每个区块的每个主问题都被问到，且追问次数有硬上限
- **AI**：在当前这一问上，怎么问得自然、怎么追问得深

每个区块**各记各的进度**，互不干扰：用户可以在「事情」聊到一半跳到「物品」，再跳回来接着聊。

每轮流程：应用告诉 AI「现在在哪个区块、问到第几题、已经追问几次」→ AI 回一句 `{ message, wantsFollowUp }` → 状态机据此决定留在本题还是推进下一题。

这一轮**只发一次请求**：模型先在行首给一个标记（`[追问]` / `[换题]`）表态，再写要说的话。不用 JSON 的原因是 JSON 没法边收边显示，一上流式就会看到半截花括号。模型没给标记时一律按「换题」处理 —— 少追问一次只是损失深度，漏掉一个主问题才是产品层面的失效。

追问上限 **3 层**，到顶即换题；区块内题目问完即标记完成。

**主问题问完之后，话筒不收走。** 一块聊完时输入框仍然留着，用户想再说就接着说，AI 顺着他说继续追问 —— 这段叫自由聊，只记账、不计入覆盖率。理由是：脚本问完了不等于他想说的说完了，而追问上限是防审讯用的，不该拿来捂嘴。

好处：覆盖逻辑与进度计算都是纯函数，**不连 AI 就能完整单测**。

### 3.4 结果不是终点，可以来回改

AI 第一次给出的归纳一定有偏差，所以结果页不是只读的：

- **清单可改** —— 事情 / 人际 / 物品 / 悬着，每一条都能编辑、删除、新增
- **计划是建议** —— 下周计划标注为「AI 建议」，用户可以放手改
- **可以重新整理** —— 用户补充一句话，AI 重写「本周热点」与「下周计划」

这里有一条明确约定：**重新整理只重写热点和下周计划，清单内容尊重用户的修改。** 否则用户辛苦改完的清单会被一次点击抹掉。

### 3.5 刷新不丢

聊了五分钟刷新一下全部消失，会非常恼火。会话过程与最近一次结果都保存在本地。

> 现状注记：**结果**这一半是落实的（每次改动结果都会落盘），但**采访过程**目前还没落盘 ——
> 聊到一半关掉应用，对话会丢。这条差距记在第十二节，属于已知未完成项，不算已兑现。

### 3.6 采访者是可以自己调的

每个人想要的「陪聊」不一样：有人要温和的朋友，有人要话少不客套的搭档。所以语气不写死。

设置页里放四套预设当起点（温和朋友 / 干脆利落 / 复盘教练 / 轻松活泛），但真正生效的是**一份可以直接编辑的完整人设提示词** —— 挑预设只是把那段文字填进编辑框，改一个字都算数，改完立刻生效，随时可以回来再改。

这里有一条边界必须说清楚，也是实现时唯一容易做坏的地方：

- **语气归用户** —— 怎么说话、要不要接话、话长话短，全在可编辑的那段文字里
- **协议归代码** —— 行首的 `[追问]` / `[换题]`、一次只问一件事、不许编造、长度上限，固定在提示词末尾，不受人设影响

原因是这两类东西的地位完全不同：前者是喜好，后者是程序还能不能跑（见 3.3，标记是流式界面和状态机推进的依据）。把它们混在一起交给用户改，等于把「跑不跑得动」也交出去了。

## 四、核心流程

```
打开
 ├→ 设置页（首次）：填 API Key / 接口地址 / 模型名；顺手调一下采访者人设（之后随时可改）
 └→ 采访页
     │   事情 │ 人际 │ 物品 │ 状态        ← 顶部四个词，点一下整页切换
     │   发送下面另有一排「聊一聊XX」      ← 不用回到顶部，随时换一块
     │   对话区只显示当前这一块，AI 一问一答、可追问；主问题聊完还能接着说
     └→ 结果页：事情 / 人际 / 物品 / 悬着 + 本周热点 + 下周计划
         ├→ 任意一条都可以直接修改、删除、新增
         └→ 补充一句 → AI 重新整理 → 回到结果页
```

## 五、功能范围

### 本版要做

| # | 功能 | 说明 |
|---|---|---|
| 1 | 设置页 | 填 API Key、接口地址、模型名，本地保存 |
| 2 | 采访页 | 顶部四个词（事情/人际/物品/状态），点一下整页切换；**发送按钮下面另有一排「聊一聊XX」**；块内 AI 一问一答、支持追问 |
| 3 | 结果清单 | **事情 / 人际 / 物品 / 悬着 各自独立成栏**，每条可修改、删除、新增 |
| 4 | 下周计划 | AI 给出建议；用户补充一句话，AI 重新整理 |
| 5 | 导出与留存 | 复制全文；关掉再开能看回上次结果 |
| 6 | 专属采访者 | 四套预设起步，**真正生效的是一份可编辑的人设提示词**，改完立刻生效、随时可改 |

### 本版不做

- **平时记录功能** —— 与「采访式回忆」重复，且会显著加重产品
- **历史记录列表、周与周对比** —— 先验证单次是否有价值
- **任何统计图表** —— 没有数据支撑，图表只会是空的
- **账号、云同步、分享** —— 个人自用工具，本地优先
- **手机端** —— 先做桌面

## 六、采访脚本（首版）

| 区块 | 主问题 | 追问方向 |
|---|---|---|
| 事情 | 这周主要忙了些什么？ | 哪件最花时间？后来结果怎么样？ |
| 事情 | 有没有本来打算做、结果没做成的事？ | 卡在哪一步？ |
| 事情 | 有没有哪件事比预想的顺利，或者比预想的费劲？ | 当时你是怎么处理的？ |
| 事情 | 这周有没有突然插进来、打乱你计划的事？ | 后来怎么安排的？ |
| 人际 | 这周跟谁打交道最多？ | 有没有卡在对方那里？ |
| 人际 | 有没有想联系、但一直没联系的人？ | 为什么一直没联系？ |
| 人际 | 有没有谁帮了你、或者你帮了谁的忙？ | 后来你们是怎么说的？ |
| 人际 | 这周有没有哪次沟通，让你觉得挺费劲的？ | 费劲在哪一步？ |
| 物品 | 这周买了什么、或者添置了什么东西？ | 买它是因为什么？用下来感觉怎么样？ |
| 物品 | 有没有处理掉、退掉、或者卖掉的东西？ | 现在回头看，这笔值不值？ |
| 物品 | 这周有没有花得不太值的一笔钱？ | 当时是怎么定下来的？ |
| 物品 | 有没有一直想买、但还没下手的东西？ | 是什么让你迟迟没定下来？ |
| 状态 | 这周整体感觉怎么样，累不累？ | 主要是被什么影响的？ |
| 状态 | 睡眠和精神头怎么样？ | 这种状态持续多久了？ |
| 状态 | 这周有没有哪个瞬间让你觉得挺舒服、挺值的？ | 那你打算怎么调整？ |
| 状态 | 还有什么我没问到、但你想说的？ | — |

十六个主问题，加上追问通常落在 25~35 轮。但因为是分块的，**用户随时可以只聊其中一块就收工**；而且一块的主问题问完之后，想继续说还能接着说（见 3.3）。

> 首版是每块 2 个主问题、追问上限 2 层，实际用下来一块三四轮就没了 —— 想多说的用户会被脚本挡住。
> 所以扩成每块 4 个主问题、追问上限 3 层，并把「问完之后」这段交还给用户。

### 「物品」这一栏的定位

这一栏来回改过两次，最终定成一句话：

> **这周买了什么、处理掉了什么。**

刻意**不做成库存管理，也不做成记账** —— 那会变成另一个产品。它只是「这周添置 / 处理了什么」的一笔记录，落进结果页是一栏清单，和其他栏一样可改可删。

## 七、结果页

```
事情           · 改了三版方案，还没定          ← 每条可改 / 可删 / 可加
               · 季度数据一直没整理

人际           · 老王 — 方案卡在他那儿没拍板
               · 张总 — 想约但一直没开口

物品           · 买了个新键盘，纠结半个月终于下单
               · 把旧手机挂二手平台卖掉了

悬着           · 报销拖了两周没交

本周热点       ● 这周基本被客户那个方案拖着 —— 来回改三版还卡在等拍板，   ← 第一条是「主线」，一句判断
                 其他事都是插空做的
               · 累的来源不是事情多，是「等」和「反复」：等拍板、等财务    ← 后面几条只写清单里
                 说清楚、评审会一超就把下午占满                            看不到的东西
               · 比上周好一点，至少有一件事是真正推完了的

下周计划  [AI 建议]
  三件重点     3 条，可直接改
  要跟进的人   2 个
  ┌ 补充一句，比如：下周必须把报价发出去…
  └ [ 让 AI 重新整理 ]     ← 只重写热点和下周计划，清单不动
                                            [ 复制全文 ]
```

结果由第二次 AI 调用生成，以结构化 JSON 返回。

**AI 返回的 JSON 一定会偶尔不合法**，解析层必须带容错与降级，不允许崩溃。

### 「本周热点」为什么不是「值得记住的几件事」

这一栏原来是「3~5 条值得记住的事」。2026-09-29 第一次拿真模型体检，发现它**退化成了清单的复印件**：events 里写过什么，就换个说法再列一遍（`改客户方案来回三版还没定` → `改客户方案来回三版还没定`），既没有取舍也没有观点。而第十一节写着，这一栏值不值得看第二遍就是项目的生死线 —— 一份复印件当然不值得。

改了三轮提示词才落地，中间那轮的错误值得记下来：第二版写的是「后面几条写支撑它的事实」—— **而事实全都躺在清单里**，等于请模型去清单里抄，实测支撑条果然还是复述。现在的规矩是：

1. **第一条必须是这一周的主线**：一句话说清「这周到底是怎么回事」，要有判断（例：「这周基本被客户方案拖着，其他事都是插空做的」）
2. **后面 2~3 条只写清单里看不到的东西**：为什么是这样、代价是什么、什么在反复出现、跟上周比有什么变化。**不写「做了什么」** —— 那是清单那一栏的活
3. 判断标准：如果某条支撑能在 events / people / things / pending 里找到意思相近的一句，就重写它

改完实测（同一份假对话、同一个模型）：热点从「5 条清单复印件」变成「1 句主线 + 3 条归纳」。其中一条是「累的来源不是事情多，是『等』和『反复』」—— 这句话在清单里任何一栏都读不到，**它才是这一栏存在的理由**。

结果页里这条主线的背景色与字重都和别的条目不同，导出成 Markdown 时也标成 `**主线**：…`，免得粘到别处又退化成一串并列条目。

## 八、技术方案

> 本节只列结论。选型理由、分层规则、四个核心决策与已知代价，见 **`技术方案.md`**。

| 层 | 选型 | 说明 |
|---|---|---|
| 外壳 | Electron | 本机已具备 Node 24，无需额外环境；主进程写薄，便于日后更换 |
| 前端 | React + TypeScript + Vite | |
| 网络层 | `ChatTransport` 接口，双实现 | 业务逻辑不直接碰网络。浏览器里用 fetch（dev 期经 Vite 代理绕开跨域）；Electron 里换成主进程 IPC，上层一行不用改 |
| 提示词 | `core/prompts.ts` 纯函数 | 「模型到底被告知了什么」本身可测，状态机的覆盖保证才算真正落地 |
| AI | OpenAI 兼容 `/chat/completions`，SSE 流式 | 兼容 DeepSeek 等，可随时更换模型 |
| 存储 | 本地 JSON 文件（两个：配置、最近一次会话） | 打包版由主进程读写；浏览器模式仍用 localStorage |
| 测试 | Vitest | 见第十节 |

**没填 API Key 就用内置的假 AI。** 这样第一次打开的人什么都不用配也能把整个流程走一遍，填上 Key 立刻切到真模型 —— 两条路走的是同一个 `AiClient` 接口。

### 已知取舍

- **包体积约 150MB** —— 个人自用可接受；体积优势只在分发给他人时才值钱
- **API Key 明文存于本机** —— 个人工具可接受，但需知悉
- **开发期请求要经本地代理** —— 浏览器直连接口会撞跨域，所以 dev 时由 Vite 代转发（转发目标来自请求头，所以换任何 OpenAI 兼容接口都能用）。Key 会经过这条本地链路，仅限本机自用；M4 改成主进程发请求后，这一步彻底消失
- **不选 Tauri 的原因** —— 本机没有 Rust 工具链，配置成本远超 MVP 阶段的收益

### 为将来更换外壳留的口子

主进程只承担「读写本地文件」与「发起网络请求」，不承载任何业务逻辑；业务逻辑全部放在前端与共享层。这样日后换成 Tauri，前端代码可 100% 复用。

这件事现在已经是**代码里的一条真实接缝**，不只是约定：所有网络请求都要经过 `core/chatTransport.ts` 里的 `ChatTransport`，浏览器那份实现单独放在 `transport/browserTransport.ts`。M4 只需要再写一份走 IPC 的实现、把注入的那一行换掉，`core/` 和 `ui/` 一行都不用动。

## 十、测试要求

当前 268 个用例，全部通过，且**一个都不依赖网络**。覆盖：

- **分块状态机** —— 区块覆盖、追问上限、区块间互不干扰、自动收起、覆盖率单调、越界降级
- **想继续说** —— 主问题问完后题目不再推进、覆盖率不再变化，但这一段被记下来；自由聊不受追问上限约束；每块主问题不少于 4 个（扩容不会再被改回去）
- **专属采访者** —— 预设原文认得出来、改一个字就当成自己写的、机器约定必须排在人设之后、人设留空退回默认、旧版本没有这一项也能读
- **编辑操作** —— 增删改、越界不生效、空白忽略、不可变性
- **AI 返回解析** —— 合法 JSON / 被 markdown 包裹 / 字段缺失 / 完全非法 → 降级不崩
- **结果导出** —— 章节完整、内容不丢、空结果有占位
- **模拟 AI** —— 人名识别、非回答过滤（「没有」不能变成一条记录）、重新整理尊重手工修改
- **SSE 流解析** —— 一个事件被切开、一包里塞多个事件、汉字被切在两个数据包之间、注释行、`[DONE]`、上游把错误塞进流里
- **传输层（浏览器）** —— 地址拼装、401/404/429 翻译成人话、连不上、模型返回空、网关整段返回 JSON 的兜底
- **传输层（主进程）** —— 请求原样交给主进程、增量一段段回传、失败还原成人话、取消转达、两次请求不串台
- **主进程落盘** —— 真写临时目录：往返、坏文件/空文件当没有、目录自动创建、先写临时文件再改名、清会话不误删配置
- **真实模型客户端** —— 行首标记的解析与摘除、追问次数以状态机为准、每轮只发一次请求、解析失败降级、重新整理时保住用户手改的清单
- **提示词** —— 进度与追问次数确实交给了模型、到顶时只能换题、未知区块不抛错
- **分层约束** —— 纯逻辑层不碰 React / 网络 / 浏览器 API，主进程逻辑不碰 Electron，外壳里不写业务

提供 mock AI（`instant` 模式）支撑测试，**不依赖真实网络**。

另有一个**启动冒烟测试**：`npm run smoke` 跑源码，`npm run smoke:packaged` 跑
`release/win-unpacked` 里那个 exe。它真的把应用拉起来，查三件事：窗口能不能开、
页面挂不挂得上（白屏是最常见的翻车方式）、桥在不在；再验一次存储确实落到了文件、
以及一次走主进程的请求失败时给的是人话。这三件事单测都帮不上忙。

还有一个**真模型试跑台**：`npm run try:model`。它用一份写死的假用户回答，拿真 Key 把
一整场采访真的跑完（含追问、四个区块），再生成一次结果，最后把整场对话原文、
行首标记遵循率、单轮耗时和那份 JSON 写成一份报告（`demo/live-output/`）。
机械性质它替你验，**质量要人看** —— 报告末尾列的就是要看的那几条，其中一条是本节的生死线。
它刻意不进 `npm test`：要联网、要花钱、还慢。

## 十一、待验证的假设与风险

| 假设 | 若不成立怎么办 |
|---|---|
| AI 问的问题问得对 | 调整脚本与 prompt；极端情况退回固定问题清单。<br>2026-09-29 真模型实测：**追问确实抓细节**（「是躺下不容易睡着，还是中间会醒？」），这条初步成立 |
| 归纳出的清单像自己这一周 | 提高追问深度；结果页已支持手动修正，可直接改。<br>实测：四栏清单与人名基本准确，「悬着」也能自动认出来；**但「本周热点」没有取舍**，见下一行 |
| **分块自选比线性问答更好** | 若用户反而觉得「不知道点哪个」，可退回线性流程 + 允许跳过 |
| **「物品」这一栏用户真的想说** | 若每次都是空栏，就砍掉，降到普通标签 |
| 最后那份热点会想看第二遍 | **这是项目的生死线**。若否定，应考虑停做，而非加功能。<br>2026-09-29 首次体检：追问质量过关，但热点是清单的复印件。当天改了三轮提示词后重跑 —— **第一条「主线」已经稳定是有判断的总结**，支撑条 2 次里 1 次真有增量（见第七节）。**样本只有 2 次，还不能算解决**，下一步该多跑几次再定 |
| 一周只用一次但能坚持 | 接受低频。怕的不是用得少，而是每次都很平庸 |
| **语气交给用户自己调，比替他定一套更好** | 若实际发现没人愿意改、或改完反而更差，就退回固定一套语气 + 只留预设切换 |
