# AI 周报 · 产品设计文档（MVP）

**版本** v0.4 ｜ **状态** 已确认，M2 已接入真实模型

---

## 一、一句话定位

> 周末坐下来跟 AI 聊五分钟，得到一份属于自己这一周的总结，和下周的计划。

---

## 二、要解决的问题

**问题不在「整理」，在「没有东西可整理」。**

目标用户平时不写周报、不做记录。到了周末想复盘，打开一个空白输入框，脑子里一片空白，写两行就关掉，此后再也不打开。

| 常见做法 | 为什么不行 |
|---|---|
| 给一个输入框让他写 | 没有素材，直接卡死 |
| 做一个记录系统让他平时记 | 要改变习惯，成本高，而他本来就不记 |
| 做统计图表 | 没有数据，图表全是空的 |

**结论：不要让他「想起来」，只要让他「回答」。**

回答一个问题，比凭空回忆容易十倍。

## 三、核心设计

### 3.1 AI 来采访你，而不是你对着空框写

打开软件，AI 先开口问一个问题；你随口答，AI 顺着追问。你只需要回答，不需要组织语言，也不需要先想好要写什么。

### 3.2 分块采访：四个词摆在顶上，点一下整页切换

采访内容分为四个区块：**事情 / 人际 / 物品 / 状态**。

这四个词**并排放在界面顶部**，点哪一个，整个对话区就切到哪一块：

- 每个词上带状态：未开始 / `1/2` / `✓`
- 对话区是一整页，只显示当前这一块的问答
- 一块聊完，按钮变成「接着聊『物品』→」，一键跳过去
- 四块都聊完（或用户中途想收工），点「生成我的本周梳理」

这样做的理由只有一个：**被人牵着走的对话，一旦用户对当前话题没兴趣，整场就断了。** 让他自己掌握进度，他才愿意多待一会儿。

> 曾经试过把四块做成同屏的折叠卡片，体验很差 —— 卡片展开后对话区被压得很扁，还要在一屏里同时看四摊东西。改成整页切换后，注意力只在一个地方。

### 3.3 状态机管覆盖，AI 管对话

**这是本产品最重要的一个设计决定。**

如果让 AI 自己决定问什么，它一定会偏——逮着一个话题聊十轮，漏掉一整块内容。

所以两者分工：

- **应用（状态机）**：保证每个区块的每个主问题都被问到，且追问次数有硬上限
- **AI**：在当前这一问上，怎么问得自然、怎么追问得深

每个区块**各记各的进度**，互不干扰：用户可以在「事情」聊到一半跳到「物品」，再跳回来接着聊。

每轮流程：应用告诉 AI「现在在哪个区块、问到第几题、已经追问几次」→ AI 回一句 `{ message, wantsFollowUp }` → 状态机据此决定留在本题还是推进下一题。

这一轮**只发一次请求**：模型先在行首给一个标记（`[追问]` / `[换题]`）表态，再写要说的话。不用 JSON 的原因是 JSON 没法边收边显示，一上流式就会看到半截花括号。模型没给标记时一律按「换题」处理 —— 少追问一次只是损失深度，漏掉一个主问题才是产品层面的失效。

追问上限 **2 层**，到顶即换题；区块内题目问完即标记完成。

好处：覆盖逻辑与进度计算都是纯函数，**不连 AI 就能完整单测**。

### 3.4 结果不是终点，可以来回改

AI 第一次给出的归纳一定有偏差，所以结果页不是只读的：

- **清单可改** —— 事情 / 人际 / 物品 / 悬着，每一条都能编辑、删除、新增
- **计划是建议** —— 下周计划标注为「AI 建议」，用户可以放手改
- **可以重新整理** —— 用户补充一句话，AI 重写「本周热点」与「下周计划」

这里有一条明确约定：**重新整理只重写热点和下周计划，清单内容尊重用户的修改。** 否则用户辛苦改完的清单会被一次点击抹掉。

### 3.5 刷新不丢

聊了五分钟刷新一下全部消失，会非常恼火。会话过程与最近一次结果都保存在本地。

## 四、核心流程

```
打开
 ├→ 设置页（首次）：填 API Key / 接口地址 / 模型名
 └→ 采访页
     │   事情 │ 人际 │ 物品 │ 状态        ← 顶部四个词，点一下整页切换
     │   对话区只显示当前这一块，AI 一问一答、可追问
     └→ 结果页：事情 / 人际 / 物品 / 悬着 + 本周热点 + 下周计划
         ├→ 任意一条都可以直接修改、删除、新增
         └→ 补充一句 → AI 重新整理 → 回到结果页
```

## 五、功能范围

### 本版要做

| # | 功能 | 说明 |
|---|---|---|
| 1 | 设置页 | 填 API Key、接口地址、模型名，本地保存 |
| 2 | 采访页 | 顶部四个词（事情/人际/物品/状态），点一下整页切换；块内 AI 一问一答、支持追问 |
| 3 | 结果清单 | **事情 / 人际 / 物品 / 悬着 各自独立成栏**，每条可修改、删除、新增 |
| 4 | 下周计划 | AI 给出建议；用户补充一句话，AI 重新整理 |
| 5 | 导出与留存 | 复制全文；会话中途不丢，关掉再开能看回上次结果 |

### 本版不做

- **平时记录功能** —— 与「采访式回忆」重复，且会显著加重产品
- **历史记录列表、周与周对比** —— 先验证单次是否有价值
- **任何统计图表** —— 没有数据支撑，图表只会是空的
- **账号、云同步、分享** —— 个人自用工具，本地优先
- **手机端** —— 先做桌面

## 六、采访脚本（首版）

| 区块 | 主问题 | 追问方向 |
|---|---|---|
| 事情 | 这周主要忙了些什么？ | 哪件最花时间？后来结果怎么样？ |
| 事情 | 有没有本来打算做、结果没做成的事？ | 卡在哪一步？ |
| 人际 | 这周跟谁打交道最多？ | 有没有卡在对方那里？ |
| 人际 | 有没有想联系、但一直没联系的人？ | 为什么一直没联系？ |
| 物品 | 这周买了什么、或者添置了什么东西？ | 买它是因为什么？用下来感觉怎么样？ |
| 物品 | 有没有处理掉、退掉、或者卖掉的东西？ | 现在回头看，这笔值不值？ |
| 状态 | 这周整体感觉怎么样，累不累？ | 主要是被什么影响的？ |
| 状态 | 还有什么我没问到、但你想说的？ | — |

八个主问题，加上追问约 15 轮。但因为是分块的，**用户随时可以只聊其中一块就收工**。

### 「物品」这一栏的定位

这一栏来回改过两次，最终定成一句话：

> **这周买了什么、处理掉了什么。**

刻意**不做成库存管理，也不做成记账** —— 那会变成另一个产品。它只是「这周添置 / 处理了什么」的一笔记录，落进结果页是一栏清单，和其他栏一样可改可删。

## 七、结果页

```
事情           · 改了三版方案，还没定          ← 每条可改 / 可删 / 可加
               · 季度数据一直没整理

人际           · 老王 — 方案卡在他那儿没拍板
               · 张总 — 想约但一直没开口

物品           · 买了个新键盘，纠结半个月终于下单
               · 把旧手机挂二手平台卖掉了

悬着           · 报销拖了两周没交

本周热点       3~5 条，这周真正值得记住的

下周计划  [AI 建议]
  三件重点     3 条，可直接改
  要跟进的人   2 个
  ┌ 补充一句，比如：下周必须把报价发出去…
  └ [ 让 AI 重新整理 ]     ← 只重写热点和下周计划，清单不动
                                            [ 复制全文 ]
```

结果由第二次 AI 调用生成，以结构化 JSON 返回。

**AI 返回的 JSON 一定会偶尔不合法**，解析层必须带容错与降级，不允许崩溃。

## 八、技术方案

> 本节只列结论。选型理由、分层规则、四个核心决策与已知代价，见 **`技术方案.md`**。

| 层 | 选型 | 说明 |
|---|---|---|
| 外壳 | Electron | 本机已具备 Node 24，无需额外环境；主进程写薄，便于日后更换 |
| 前端 | React + TypeScript + Vite | |
| 网络层 | `ChatTransport` 接口，双实现 | 业务逻辑不直接碰网络。M2/M3 用浏览器 fetch（dev 期经 Vite 代理绕开跨域），M4 换成主进程 IPC，上层一行不用改 |
| 提示词 | `core/prompts.ts` 纯函数 | 「模型到底被告知了什么」本身可测，状态机的覆盖保证才算真正落地 |
| AI | OpenAI 兼容 `/chat/completions`，SSE 流式 | 兼容 DeepSeek 等，可随时更换模型 |
| 存储 | 本地 JSON 文件 | 配置与最近一次会话分开存放 |
| 测试 | Vitest | 见第十节 |

**没填 API Key 就用内置的假 AI。** 这样第一次打开的人什么都不用配也能把整个流程走一遍，填上 Key 立刻切到真模型 —— 两条路走的是同一个 `AiClient` 接口。

### 仓库结构

```
ai周报/
├── AGENTS.md
├── docs/
│   └── 产品设计文档.md      ← 本文档
└── demo/                    ← 可运行的 Demo
    ├── package.json
    ├── vite.config.ts       含 dev 期的模型接口代理（绕开跨域）
    └── src/
        ├── core/            ← 纯逻辑，全部可单测
        │   ├── script.ts        采访脚本（区块、主问题、追问话术）
        │   ├── interview.ts     分块状态机
        │   ├── aiClient.ts      AI 能力接口
        │   ├── mockAi.ts        演示用假 AI
        │   ├── openAiClient.ts  真实模型实现
        │   ├── createAiClient.ts 按配置挑实现（填了 Key 就用真的）
        │   ├── chatTransport.ts 传输层接口 —— 唯一碰网络的地方
        │   ├── prompts.ts       提示词构建
        │   ├── sse.ts           SSE 流解析
        │   ├── turn.ts          行首标记的解析与摘除
        │   ├── aiError.ts       失败翻译成人话
        │   ├── parseResult.ts   模型 JSON 容错解析
        │   ├── refineMerge.ts   重新整理时的清单保护
        │   ├── resultEdit.ts    结果编辑操作
        │   └── resultText.ts    导出 Markdown
        ├── transport/       ← 传输层实现；M4 在这里加一份走 IPC 的
        ├── storage/         ← 本地留存
        └── ui/              ← 页面
```

**`core/` 里不出现任何 React**，全部是纯函数，所以可以脱离界面完整测试。

### 已知取舍

- **包体积约 150MB** —— 个人自用可接受；体积优势只在分发给他人时才值钱
- **API Key 明文存于本机** —— 个人工具可接受，但需知悉
- **开发期请求要经本地代理** —— 浏览器直连接口会撞跨域，所以 dev 时由 Vite 代转发（转发目标来自请求头，所以换任何 OpenAI 兼容接口都能用）。Key 会经过这条本地链路，仅限本机自用；M4 改成主进程发请求后，这一步彻底消失
- **不选 Tauri 的原因** —— 本机没有 Rust 工具链，配置成本远超 MVP 阶段的收益

### 为将来更换外壳留的口子

主进程只承担「读写本地文件」与「发起网络请求」，不承载任何业务逻辑；业务逻辑全部放在前端与共享层。这样日后换成 Tauri，前端代码可 100% 复用。

这件事现在已经是**代码里的一条真实接缝**，不只是约定：所有网络请求都要经过 `core/chatTransport.ts` 里的 `ChatTransport`，浏览器那份实现单独放在 `transport/browserTransport.ts`。M4 只需要再写一份走 IPC 的实现、把注入的那一行换掉，`core/` 和 `ui/` 一行都不用动。

## 十、测试要求

当前 176 个用例，全部通过，且**一个都不依赖网络**。覆盖：

- **分块状态机** —— 区块覆盖、追问上限、区块间互不干扰、自动收起、覆盖率单调、越界降级
- **编辑操作** —— 增删改、越界不生效、空白忽略、不可变性
- **AI 返回解析** —— 合法 JSON / 被 markdown 包裹 / 字段缺失 / 完全非法 → 降级不崩
- **结果导出** —— 章节完整、内容不丢、空结果有占位
- **模拟 AI** —— 人名识别、非回答过滤（「没有」不能变成一条记录）、重新整理尊重手工修改
- **SSE 流解析** —— 一个事件被切开、一包里塞多个事件、汉字被切在两个数据包之间、注释行、`[DONE]`、上游把错误塞进流里
- **传输层** —— 地址拼装、401/404/429 翻译成人话、连不上、模型返回空、网关整段返回 JSON 的兜底
- **真实模型客户端** —— 行首标记的解析与摘除、追问次数以状态机为准、每轮只发一次请求、解析失败降级、重新整理时保住用户手改的清单
- **提示词** —— 进度与追问次数确实交给了模型、到顶时只能换题、未知区块不抛错

提供 mock AI（`instant` 模式）支撑测试，**不依赖真实网络**。

## 十一、待验证的假设与风险

| 假设 | 若不成立怎么办 |
|---|---|
| AI 问的问题问得对 | 调整脚本与 prompt；极端情况退回固定问题清单 |
| 归纳出的清单像自己这一周 | 提高追问深度；结果页已支持手动修正，可直接改 |
| **分块自选比线性问答更好** | 若用户反而觉得「不知道点哪个」，可退回线性流程 + 允许跳过 |
| **「物品」这一栏用户真的想说** | 若每次都是空栏，就砍掉，降到普通标签 |
| 最后那份热点会想看第二遍 | **这是项目的生死线**。若否定，应考虑停做，而非加功能 |
| 一周只用一次但能坚持 | 接受低频。怕的不是用得少，而是每次都很平庸 |
